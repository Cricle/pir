# 0.3.4 direction: small, medium and large tasks that execute accurately and efficiently

Research note, 2026-11-27. Every figure below is measured on this tree,
not copied from an older document. Where a number is a design target rather
than a measurement it says so.

The goal for 0.3.4: **one release, one binary, and the right lane for the
job.** A user states a task; pir decides how much machinery that task
warrants, guarantees the task actually completed, and does not spend
foreman-sized effort on a one-file fix. `pir-durable` is the backbone that
makes a multi-step task survive a restart, not an optional extra.

Two consequences of that framing, both deliberate:

- **There is no light profile and no second binary.** 0.3.4 ships `full`
  only. Binary size stops being a goal; §1 keeps the measurements only
  because they explain *why* the lane decision matters and why "just strip
  features" is not a substitute for it.
- **Efficiency is measured per task, not per binary.** The same task costs
  3–5× more in different lanes (§1.2). Choosing the lane badly is a much
  larger waste than any byte count on this page.

**What 0.3.4 actually ships is two lanes, not three, and that is on
purpose.** Small and Large have guarantees that work without a human in the
loop; Medium's stronger guarantee needs a task record that does not exist
until B lands (§5, D3). The document keeps the three-size model because it
is the target, and states which parts of it are wired rather than assuming
all three are equal on day one — §1 of this tree's own history is a list of
claims that were not measured, and this is the one most likely to be
repeated.

## 1. What each lane costs, and what each one guarantees

### 1.1 The lanes and their guarantees

The dispatch is one function, `gate_continuation`
(`plugins/builtin/mode/mod.rs:999-1008`):

```rust
if mode == Mode::Foreman { return self.foreman_gate_continuation(payload); }
if mode == Mode::Normal  { return self.contract_gate_continuation(payload); }
None    // Plan: plan mode never gates a run
```

| lane | correctness mechanism | where |
|---|---|---|
| `normal`, no approved plan | **none.** `contract_gate_continuation` returns `None` at `active_contract()?`; a tool error is a result and the loop continues. | `mod.rs:1081` |
| `normal`, approved plan | **execution contract**: not done until a declared verification command exits 0 **after the last mutation**; a claim of "verified" does not count. 3 nudges, then UNVERIFIED. | `mod.rs:1080-1131`, `verification_evidence_passed` `:2173` |
| `plan` | **no gate by design** — it produces the plan, then switches the session to Normal on approval (`mod.rs:2959-2966`) so the contract governs execution | `mod.rs:1008` |
| `foreman` | **independent reviewer**: no worker counts as delivered until a `reviewer` replies `{"verdict":"PASS"}`; an errored/aborted/`length` worker is a failure the gate rejects even if a reviewer says PASS. 3 nudges, then UNVERIFIED. | `GATE_MESSAGE` `mod.rs:137`; `is_failed` `pir-builtin-subagent/src/lib.rs:571` |

So today the mode is a **user** decision (`/mode`, `mod.rs:1891`), and the
cheapest lane is the only one with **no** correctness guarantee. That is the
precise defect 0.3.4 fixes: the fast path must not be the unverified one.

### 1.2 Efficiency, measured per task (N=1, debug, same task each row)

From `RESULTS.md` — the same build-a-browser-game task, same gateway/model,
one lane per row:

| run | `normal` | `plan` | `foreman` |
|---|---:|---:|---:|
| 2026-11-20 | 273,035 tok / 11 turns | 484,315 / 21 | 724,832 / 47 |
| 2026-11-21 | 418,733 / 15 | 718,755 / 23 | 1,166,133 / 43 |
| re-run | 452,144 / 16 | **1,147,051** / 31 | 776,419 / 37 |

Two readings that matter for lane selection:

1. **The spread is 3–5×**, so a wrong lane costs more than any binary
   sizing question in this document ever could.
2. **The lanes are not ordered by cost.** `plan` was *more* expensive than
   `foreman` in the last run (1,147,051 vs 776,419) and more expensive than
   `normal` in two of three. "Bigger task → heavier lane" is not safely
   assumed; it has to be measured per task, which is exactly why D2 is a
   regression-tested function rather than a heuristic.

Correctness in the same runs is not uniform either: on 2026-11-21 the
approved `plan` shipped an artifact whose first frame crashed
(`drawPlayer` read `p.invuln` with `p` null) while its static checks passed —
the contract gate faithfully accepted the checks the plan declared. The
re-run added a runtime smoke command to the plan and it passed. That is the
concrete case for D1: **what a lane verifies is a product decision, and the
default must be "actually ran", not "looks right".**

### 1.3 Why "strip features" is not the substitute

Kept only as context, because it is the obvious wrong answer to "efficient".

| | full (`pir`) | `pir-minimal` (zero features) |
|---|---:|---:|
| release binary (Windows GNU, thin LTO, strip) | **73.3 MiB** | **13.7 MiB** |
| unique cargo packages | **436** | **149** |
| warm startup (`--version`) | **44–48 ms** | **44–62 ms** |
| tools declared by default | **12** | **1** |
| whole first-turn request | **20,381 B** | **767 B** |

Measured additively from a 186-package core-tools baseline, the heavy
carriers are `mcp` +130 (mostly the `extensions` it depends on), `extensions`
+104, `brush` +93, `tui` +41, `image-tools` +20.

`brush` is the embedded bash-compatible shell and is the **last-resort
fallback** when no bash exists (`coding_agent/tools/bash.rs:936-941`,
`:949-958`) — it is the only thing that makes the `bash` tool work on a
Windows machine with no Git Bash, so it stays.

The point: the binary is big and the request is 26× the minimal one, but
**none of that is fixed by shipping a smaller binary** for 0.3.4's goal. A
13.7 MiB agent that picks the wrong lane still burns 3–5× the tokens. Size
work is deferred; correctness and lane selection are not.

### 1.4 The per-turn cost that lane selection can actually reduce

The recurring cost is the request payload, and it is the one thing a lane
decision changes:

| | full default | what a small-task lane could declare |
|---|---:|---:|
| `tools[]` JSON per request | **15,670 B** | ~4,000 B (4–6 tools) |
| system prompt | **4,538 B** | shorter: no foreman/plan contract text |
| whole first-turn request | **20,381 B** | ~9,000 B |

Paid on **every turn**, unlike the binary. §1.2 shows the same task in
`foreman` cost 47 turns once; at 20,381 B of fixed payload that is ~1 MB of
pure schema before any work happens. Declaring fewer tools for a small task
is the cheap half of "efficient", and it does not require a second binary.

## 2. What a multi-step task is missing (read from the code, not aspirational)

The engine already has more autonomy machinery than its defaults use.

**Already there and real:**

- A bounded turn loop with a **degenerate-loop guard**: 20 identical
  single-tool turns inject a steering nudge, a second streak stops the run
  (`agent/agent_loop.rs:4071`, `:3177-3298`). Measured against a real
  runaway of 487 identical calls.
- **Steering** (`OneAtATime` by default) lets a user redirect between tool
  batches inside one turn; **follow-up** queues drain only when the tool
  loop stops (`agent_session/queue.rs`, `agent_loop.rs:3405-3492`).
- Tool errors are **results, not failures**: an `is_error` message is
  persisted and the loop continues (`agent_loop.rs:2703-2708`).
- `tool-repair` repairs malformed assistant messages before they reach the
  context.
- `subagent` + `mode` (foreman/plan) give delegation with approvals and a
  durable journal.
- Compaction preserves a recent window and summarizes the rest.

**Already there but UNWIRED — the big opportunity:**

`pir-durable` (56k lines) has a complete long-horizon runtime:
`TaskScheduler` with named **phases**, **checkpoints**, foreground and
background **timers**, per-task **usage accounting**, an inbox, and a
document store.

It is reachable today, but **never from a default session** — and the two
reachable paths are both hand-built, not driven by the agent loop:

| path | state |
|---|---|
| Rust API (`pir::durable::…`) | Real and tested. `tests/durable_session_lane_e.rs`, `tests/g_durable_integration.rs`, `examples/dev_durable_timers.rs`, `examples/dev_durable_reports.rs` exercise storage, the session kernel and host timers. Usable only by an embedder writing code against it. |
| JS extension (`import "@earendil-works/pi-durable"`) | Storage, `createSession`, `ExecutionEnv`, `/tools`, `/codemode` are ported and importable. **But `Harness`, `createRegistry` and `watchEvents` throw `ERR_NOT_SUPPORTED`** (`extensions/api/shims.rs:128-130`): the scheduler engine is an open decision (upstream's "D5"), not written. |
| The agent loop itself | **Nothing.** `crates/pir-core/src/lib.rs:146-147` re-exports the crate behind `feature = "durable"`, and that is the only `durable::` identifier in the engine — no `TaskScheduler`, no harness, no task record. `foreman`'s "durable state" is its own journal, unrelated to this crate. |

So the correct statement is not "the runtime has no caller" — it is
**the runtime has no *scheduler-facing* caller, on either side.** The Rust
half has a scheduler nobody in the engine invokes; the JS half exposes the
types but throws on the one entry point that would run them. Both ends stop
at the same seam, which is why connecting it (milestone B) is one job, not
two.

That is the 0.3.4 thesis in one line: **the storage, session and timer layers
that a multi-step task needs are already written and tested; what is missing
is the caller that drives them, and the correctness check that decides when
the task is actually done.**

**Missing for a task that spans turns (each is fixed by a B item):**

1. **No persistent task.** A prompt is a single run; there is no object that
   says "this task is unfinished" and survives a crash, a restart or a new
   session. `--continue` resumes a transcript, not an intention. → B1/B3.
2. **No budget accounting across turns.** Turn caps are per-prompt
   (`DEFAULT_AGENT_MAX_TURNS = 1000`, `INTERACTIVE_AGENT_MAX_TURNS = 100`);
   token budgets are per-profile. A task that takes three prompts restarts
   the count. → B1/B2.
3. **No self-critique pass.** The "final self-check" is a prompt sentence,
   not a mechanism; `efficient` even drops that sentence. → D1 is the
   mechanism that replaces it (a check must pass, not a claim).
4. **No progress signal.** The repeat guard detects *stagnation* by
   identical-call hashing, but nothing measures whether the task moved. →
   D1's check result is the first real progress signal.
5. **No scheduled continuation.** Nothing says "come back in 10 minutes and
   check the build". `jobs` and `foreman` detach *processes*, which is a
   different and heavier thing. Durable's `Timers` can already do this;
   nothing schedules through it. → B4.

## 3. Ease of use: the first five minutes are the worst part

Two concrete defects, both reproducible on a fresh agent dir with no keys:

**Defect A — the first-run wizard never asks for a model.**
`config/first_run.rs:106-160` asks for a theme and analytics consent. It
never mentions a provider or an API key. And the wizard only runs when
`PI_EXPERIMENTAL=1` (`first_run.rs:64-71`), so for a normal install it does
not run at all. A new user's first command therefore hits:

```
Error: no model available; configure a provider with `pir auth login` or
C:\...\.pi\agent\models.json
```

(`coding_agent/overrides.rs:57-64`). That message is accurate and names two
real escape hatches, but it assumes the reader already knows what a
provider, a base URL and a model id are.

**Defect B — `pir auth` is a 54-line wall, not a chooser.**
`pir auth` on a fresh dir prints 9 OAuth providers and ~25 API-key
providers, every one "unset". It is a status dump. There is no ranked
"the three that work in one command" view, no detection of an existing
`OPENAI_API_KEY`-equivalent already in the environment, and no single
command that takes a key and produces a working session.

Neither defect is about *missing features* — everything needed exists
(`auth login`, `models.json`, the provider catalog). Both are about the
**first five minutes** having no designed path through that surface.

## 5. The plan (ordered; each item names how it is accepted)

Three tracks, deliberately ordered so a milestone can ship without the
next one landing. Every item states an **acceptance check** that is a
command or a measurement, not an opinion — the point of §1 is that this
project already has the wrong kind of "light" claims and does not need
more.

### Milestone 0.3.4-B — durable as the backbone of a multi-step task

`pir-durable` becomes load-bearing here, which is the point: a task that
spans turns must survive a crash and must keep one budget across all of it.
Durable already has the scheduler, phases, checkpoints and timers; what it
does not have is a caller (§2). The work is to give it one, not to build a
new runtime.

| # | Work | Acceptance |
|---|---|---|
| B1 | Define the **task record** in `pir-durable`: id, phases, budget (turns + tokens), checkpoint, chosen lane, status. Reuse `TaskDefinition`/`define_task` (`crates/pir-durable/src/tasks.rs:19,69`) rather than a new abstraction. | A unit test opens a task, records two phases, reloads it from storage, and sees both phases — no engine involved. |
| B2 | Drive it from the engine: a task run calls the existing `agent_loop` per phase and persists the phase result through the record. | An integration test in `tests/` runs a two-phase task against the mock provider and asserts **both** phases ran and the budget was debited **once across both**. |
| B3 | Make the budget survive a restart: kill and reopen the process mid-task, resume from the checkpoint. | A test that writes a task, drops the handle, reopens from disk, and continues — asserting the turn counter did **not** reset. |
| B4 | Scheduled continuation through the existing `Timers` (`crates/pir-durable/src/timers.rs:162`), not `jobs`/`foreman`. | A test with an injected clock (the durable timers take host timers, `timers.rs:207`) that fires a continuation and asserts the task advanced with no process detached. |

B1–B3 are the milestone; B4 may slip if the clock injection fights the
engine's tokio time.

> **B2's test is the go/no-go for the whole release.** If a two-phase task
> cannot share one budget without reaching into `agent_loop`'s internals,
> then the "second harness" caveat in `durable-spec.md:18` is real, and the
> right shape is a task *inside* the loop. Find that out before writing B3/B4
> or any of D.

### Milestone 0.3.4-D — size the task and pick the mode that guarantees it

Today the mode is a **user** decision (`/mode normal|foreman|plan`,
`pir-core/src/plugins/builtin/mode/mod.rs:1891`), and the three modes do
not offer the same correctness — they offer different *kinds* of it.

The dispatch is one function, `gate_continuation` (`mod.rs:999-1008`):

```rust
if mode == Mode::Foreman { return self.foreman_gate_continuation(payload); }
if mode == Mode::Normal  { return self.contract_gate_continuation(payload); }
None    // Plan returns here: plan mode never gates a run
```

> **Correction.** An earlier revision of this document said "`plan` has the
> execution contract and `normal` has none". That is backwards and it matters
> for D1. `plan` mode is *read-only planning*; when a plan is approved the
> plugin **switches the session back to Normal** so the contract governs
> execution (`mod.rs:2959-2966`: `apply_mode_with_notice(state, Mode::Normal,
> "Plan approved. Leaving plan mode; the verification contract is active.")`).
> The contract gate is therefore installed on **Normal** and fires only when
> `active_contract()` is `Some` — which is exactly the shape D1 needs.

| mode | correctness mechanism | where |
|---|---|---|
| `normal`, no approved plan | **none.** `contract_gate_continuation` returns `None` at `active_contract()?`; a tool error is a result and the loop continues. | `mod.rs:1081` |
| `normal`, approved plan | **execution contract**: not done until a declared verification command exits 0 **after the last mutation**; a claim of "verified" does not count. 3 nudges, then UNVERIFIED. | `contract_gate_continuation` `mod.rs:1080-1131`, `verification_evidence_passed` `mod.rs:2173`, message `mod.rs:147` |
| `plan` | **no gate by design** — it produces the plan and is switched to Normal on approval | `mod.rs:1008`, `:2959-2966` |
| `foreman` | **independent reviewer**: no worker counts as delivered until a `reviewer` subagent replies `{"verdict":"PASS"}`; an errored/aborted/`length` worker is a failure the gate rejects even if a reviewer says PASS. 3 nudges, then UNVERIFIED. | `GATE_MESSAGE`, `mod.rs:137`; `is_failed` (`pir-builtin-subagent/src/lib.rs:571`) treats `length` as failure |

So "small, medium and large tasks all execute correctly by themselves" is
**not** a routing problem, and the corrected table makes the reason sharper:
the only unverified lane is plain `normal`, and everything that verifies does
so through **one** seam. The requirement is two things:

1. **size the task**, and
2. **make the contract gate reachable without a human having approved a
   plan** — which is the whole of D1, and it is smaller than the earlier
   revision claimed because the gate is *already* wired into Normal.

That second point is also why the lane table below has only two *guarantee*
levels in a headless run. Plan mode's contract is real, but reaching it
requires an approval (`submit_plan` parks a request; `delegation.rs:211-217`
tells the model to stop and wait for `/approvals` or `pir foreman approve`),
so it is a lane for interactive use, not something D3 can route a `pir -p`
task into.

| # | Work | Acceptance |
|---|---|---|
| D1 ✅ | **A verification floor for every lane.** Give `active_contract()` (`mod.rs:617`) a fallback: when no plan contract is active, synthesise one from declared checks. Declared checks have **two** producers — a new repeatable `--check <CMD>` flag, persisted per session (B) and the task record's `CheckSpec`s — so D1 works before B lands. Deliberately a flag, not a settings key: a verifier is per-project (`cargo test` here, `npm test` there) and §4's 67 flat keys are already the wrong shape. Nothing else changes: `gate_continuation` already routes Normal runs here. **Shipped 2026-11-28.** | A test drives a `normal` run whose model claims success while its declared check fails, and asserts the run is **not** reported complete and is nudged to fix it. Second case: verify, then edit, then claim done — still rejected (free, because `last_mutation` already orders it). This is the item that makes "small tasks execute correctly" true rather than hoped for. |
| D2 | **A task sizing signal**, computed before the first turn. Three inputs ship first (paths named in the prompt, touched-module count, prompt shape — deliverable count / step sequence); the fourth, "this task already failed once", reads the task record's ledger and arrives with B1. Never a model self-assessment. D3 needs this function, so **D2a (the three-input version) ships with D3**, not after it. | A table test over recorded `RESULTS.md`-style task fixtures (the `s1`/`s2`/`l1`/`c3` rows at `RESULTS.md:211-214`) where the expected lane is written down, so sizing is a **regression-tested function**, not a heuristic nobody checks. The `c3` row (24,954 tok but a plan→implement shape) is the one that fails a token-only rule. |
| D3 | **Auto lane selection** from D2's signal, with the lane's guarantee attached. What ships in 0.3.4 is **two** lanes: small → `normal` + D1's floor from a one-line `--check`; large → `foreman`. The medium lane is `normal` + D1's floor over the checks a *planned phase* wrote, so it has no producer until B1 — it is claimed only once B lands, and the ledger records which source armed the floor. **Medium is never the plan lane in a headless run**: `submit_plan` only parks an approval a human must decide (`delegation.rs:211-217`, `foreman.rs:129`) and `pir -p` has no human, so routing there would end the run waiting for a decision nobody can make. Record the chosen lane and the reason in the task record (B1) when it exists, in the session ledger until then. | A run started with no `/mode` command reports its chosen lane and reason; switching lanes mid-run is refused with a reason. Two lanes are asserted now (Small's floor fires, Large's reviewer gate fires); the Medium assertion is added with B1. |
| D4 | **Escalation on failure, never on vibes**: a lane that fails its own check twice escalates one step up (verified-`normal` → `foreman`), recording each escalation in the task record. In an interactive session the step between them is the approved-plan contract, which is available there because a human can approve. De-escalation does **not** happen automatically. | A test where the first lane fails twice and the run ends in the next lane, with both attempts and both verdicts in the task record's ledger. |
| D5 | **Declare only the tools the lane needs.** A small task declares 4–6 tools; `foreman` keeps its read-only set plus `subagent`; nothing becomes unreachable (the registry is never filtered — §1.4). **Honest scope:** this small-lane payload is already reachable today via `--perf-profile efficient`, which declares exactly `read/bash/edit/write`; D5's real content is making the right declaration automatic plus fixing lane-vs-profile precedence (today `efficient` would strip foreman's `subagent`). It is the D item to drop first if the schedule tightens. | A capture (same method as §1.4) shows a small-lane first turn under 10,000 B of `tools[]`, and a `tool_search` call still reaches an undeclared tool. |

**Order is D1 → D2a → D3 → D5 → (B1) → D2b → D4**, and D1 is not optional:
without it, D3 would route small tasks into the one lane that cannot tell
success from failure. **D1 alone is already an improvement** (every `normal`
run with a declared check gains a verification floor) and ships
independently of B, because `--check` is a producer with no dependency on
the task record.

D2 splits on the same line B does: the three-input sizing function (D2a) has
no dependency on the task record and must ship *with* D3, because D3's lane
choice is a function of it — an earlier revision listed D3 before D2 and
claimed three lanes, which is not executable. The "already failed once"
input (D2b) reads B's ledger, so it and D4 (which counts failed attempts in
the same ledger) both come after B1.

> Deliberate non-goal: D2 must not ask the model "how hard is this?".
> A self-assessment is unmeasurable, and §1's whole method is that claims
> become numbers or they do not go in the plan. Sizing uses inputs the
> harness already has.

Detect an already-set key (the same list `pir auth` prints) and offer it as the default answer instead of asking for a raw string. | On a fresh agent dir with `OPENAI_API_KEY` set and `PI_EXPERIMENTAL=1`, setup ends with a `settings.json` that a subsequent `pir -p "hi"` uses **without** the `no model available` error. |

### Suggested release shape

Since the theme is B (a durable task record) plus D (lanes that verify), the order is:

1. **D1** first, not B first. It is the item that turns "small tasks
   execute correctly" from a hope into a tested property, it needs no task
   record (`--check` is its own producer), and it improves every `normal`
   run even if nothing else lands. Shipping D1 is a complete, useful 0.3.4.
2. **D2a + D3 (two lanes) + D5 + C1/C2** — sizing, auto lane selection with
   the two guarantees a headless run can deliver (D1's floor, and foreman's
   reviewer), per-lane tool declaration, and the first five minutes. None of
   it reads the task record, so this block is a complete release if B slips.
3. **B1 + B2** next — they answer the only question that can invalidate the
   rest (see the B2 note). If they fail, stop and re-plan around what B2's
   test proved; everything in 1–2 is already out the door and unaffected.
4. **B3, D2b, D4, B4, D3 (medium)** — persistence, the ledger-backed sizing
   input, escalation, scheduled continuation, and the third lane.

D2 and D4 were previously listed beside D3 in step 3 of an earlier revision
while claiming to read B's ledger — that ordering could not be executed.
D2 is therefore split: its three-input half ships with D3, its
ledger-backed half after B1. The former keeps step 2 shippable on its own,
which is this document's whole argument.

There is **no light profile in this release**. `full` is the only binary
(`pir-minimal` continues to exist as the zero-feature developer probe, not
as a shipped product). If 0.3.4 has to ship early, ship 1 + 2 and take B to
0.3.5 rather than shipping a half-connected task record.

## 6. What must NOT change

- **Production run speed and TUI hard contracts.** 0.3.3's release was
  blocked once by a retry budget that regressed empty-file `open` from 26 ms
  to 596 ms; that class of "correct but slower" change is out.
- **Extracted crates stay independent** (`tests/version_consistency.rs`
  enforces it). Milestone B connects durable *as a consumer* through the
  `TaskRunner` trait, never by taking a dependency edge back into the
  engine. `pir-durable` and `pir-builtin-mode` have no edge either way today
  and that stays true: the lane is the mode plugin's vocabulary, so the task
  record stores the lane's *name and reason*, not a type.
- **No new runtime.** B uses the QuickJS-free durable runtime. Neither a
  second interpreter nor a second scheduler beside the one durable already
  has is on offer.

## 7. Decisions settled for 0.3.4

**Settled, with the reason:**

1. **One release, one binary: `full`.** There is no `pir-light`. The size
   measurements in §1.3 stay in the document only to explain why stripping
   features is not the answer to "efficient" — a 13.7 MiB agent that picks
   the wrong lane still burns 3–5× the tokens (§1.2). `pir-minimal` remains
   what it always was: a zero-feature developer probe that proves the
   engine's core is runnable, not a product.
2. **A task record is its own store, keyed alongside a session.** `--continue`
   users will expect resumption to follow the transcript, so the record
   carries the session id it advances; but the record itself is not a
   message in the transcript, because a task outlives one transcript and
   must be openable with no session at all (B3's test reopens it from
   disk). Storing it *as* session entries would force the two lifecycles
   to be equal, which is exactly the constraint that makes crash-resume
   work today.
3. **D1 ships first, and `--check` is why it can.** Declared checks get a
   producer that needs no task record, so the correctness floor does not
   wait on B's uncertainty. It is a repeatable flag persisted per session,
   not a settings key: a verifier is per-project, and the 67 flat keys are
   already the wrong shape (§4). This is also the reason the order changed
   — the earlier revision put B1+B2 first and gated the certain item behind
   the uncertain one.
4. **Tool selection is per lane, not per user.** D5 narrows what a small
   task declares; it never removes a tool from the registry, so
   `tool_search` and explicit `--tools` still reach everything. This is
   the difference between "efficient by default" and "crippled by default",
   and it is why D5 does not need the N>1 evidence that changing the
   *global* default would have needed. Recorded honestly: the small-lane set
   is already reachable via `--perf-profile efficient`, so D5's value is the
   default plus the precedence fix, not a new capability.
5. **A lane that needs a human is not a lane D3 can pick.** The approved-plan
   contract stays a real guarantee for interactive sessions, but D3 never
   routes a non-interactive run into it, because `submit_plan` only parks an
   approval and `pir -p` has nobody to decide it. Auto-approving that gate
   (or letting the model arm its own checks without approval) is a 0.3.5
   decision with its own safety question, not something to assume here.

**One thing to watch (not a blocker):** D5 assumes models call
`tool_search` for tools they were not handed. `RESULTS.md` has one measured
observation that supports *removing* tools nobody calls (`ctx_*`: zero calls
across six runs), but none that proves *hiding-then-discovering* works. D5's
acceptance check covers the mechanism (`tool_search` reaches an undeclared
tool); whether models use it well is a quality question to measure after
D3 ships, on real tasks, not a reason to block the wiring.
