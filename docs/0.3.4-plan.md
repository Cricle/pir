# 0.3.4 direction: an AGI-shaped agent that is lighter, not just smaller

Research note, 2026-11-27. Every figure below is measured on this tree
(`acfa567` + the release-workflow fix), not copied from an older document.
Where a number is a design target rather than a measurement it says so.

The goal for 0.3.4, stated plainly: **more autonomy per byte**. The agent
should pursue a goal across many turns, recover from its own mistakes and
know when to stop — while the thing a user installs, reads and pays for
stays small. Those two pull against each other, and today's tree pays for
both separately instead of together.

---

## 1. What "light" costs today (measured)

### 1.1 The two ends of the range

| | full (`pir`) | minimal (`pir-minimal`) | ratio |
|---|---:|---:|---:|
| release binary (Windows GNU, thin LTO, strip) | **73.3 MiB** | **13.7 MiB** | 5.4x |
| unique cargo packages | **487** | **144** | 3.4x |
| startup, warm (`--version`, 3 runs) | **44–48 ms** | **44–62 ms** | ~1x |
| tools declared by default | **12** | **1** | 12x |
| `tools[]` JSON per request | **15,670 B** | **487 B** | **32x** |
| system prompt | **4,538 B** | **129 B** | **35x** |
| whole request, first turn | **20,381 B** | **767 B** | **26.6x** |

Method: `cargo build --release --bin pir` and
`cargo build --no-default-features --release --bin pir-minimal`, both
`--target x86_64-pc-windows-gnu`. Request sizes come from a local
HttpListener capture of a real first turn (`-p "hi"` against a mock
`openai-completions` endpoint), byte counts measured on the parsed JSON,
not estimated.

> **Startup is not the problem.** The two binaries boot in the same time
> within noise. Anyone arguing "lighter" from startup latency is arguing
> from a difference that does not exist. The costs are **install size**,
> **request payload** and **surface area** — all three paid repeatedly, the
> middle one on **every single turn**.

### 1.2 Where the 59.6 MiB goes

The measured per-feature deltas in [`FEATURES.md`](FEATURES.md) §4.1 are
from a **different artifact** (external fat-LTO consumer with fat tables),
so they are not subtractable from this 73.3 → 13.7 gap. What the deltas do
establish is relative weight:

| feature | delta (their artifact) | note |
|---|---:|---|
| `mcp` | +39.85 MiB, +426 pkgs | largest single carrier |
| `extensions` (QuickJS + SWC) | +21.32 MiB, +333 pkgs | `context-mode` rides on it at +0 |
| `memory` | +4.57 MiB, +12 pkgs | store is resident |
| `tools` | +1.82 MiB | the seven core leaves |
| builtins (`todo`/`subagent`/…) | +0.07–0.70 MiB each | |

The two big carriers alone are ~61 MiB on their artifact. That is the whole
gap. So the "light" question is **not** diffuse — it is two decisions:
do you ship a JavaScript engine (`extensions`/`context-mode`), and do you
ship an MCP client? Everything else is rounding.

### 1.3 What a "light but real" agent would look like

`pir-minimal` is too thin to be useful: one `read_file` tool, no session
persistence, no shell, no edit. But it proves the floor. A credible light
profile is the gap between them:

> **full agent loop + real tools (`read`/`bash`/`edit`/`write`/`grep`/
> `find`/`ls`) + sessions + providers, without `extensions`,
> `context-mode`, `mcp`, `memory` or `tui`.**

That combination already exists as a `feature_matrix.sh` row (`no-js`,
line 155) but it is a **test row, not a shipped profile**: there is no
`pir-light` binary, no documented install path, and no measurement of
what it weighs. Measuring it is the first concrete 0.3.4 deliverable.

## 2. What "AGI-shaped" is missing (read from the code, not aspirational)

The engine already has more autonomy machinery than its defaults use.

**Already there and real:**

- A bounded turn loop with a **degenerate-loop guard**: 20 identical
  single-tool turns inject a steering nudge, a second streak stops the run
  (`agent/agent_loop.rs:4071`, `:3177-3298`). Measured against a real
  runaway of 487 identical calls.
- **Steering** (`OneAtATime` by default) lets a user redirect between tool
  batches inside one turn; **follow-up** queues drain only when the tool
  loop stops (`agent_session/queue.rs`, `agent_loop.rs:3405-3492`).
- Tool errors are **results, not failures**: an `is_error` message is
  persisted and the loop continues (`agent_loop.rs:2703-2708`).
- `tool-repair` repairs malformed assistant messages before they reach the
  context.
- `subagent` + `mode` (foreman/plan) give delegation with approvals and a
  durable journal.
- Compaction preserves a recent window and summarizes the rest.

**Already there but UNWIRED — the big opportunity:**

`pir-durable` (56k lines) has a complete long-horizon runtime:
`TaskScheduler` with named **phases**, **checkpoints**, foreground and
background **timers**, per-task **usage accounting**, an inbox, and a
document store.

It is reachable today, but **never from a default session** — and the two
reachable paths are both hand-built, not driven by the agent loop:

| path | state |
|---|---|
| Rust API (`pir::durable::…`) | Real and tested. `tests/durable_session_lane_e.rs`, `tests/g_durable_integration.rs`, `examples/dev_durable_timers.rs`, `examples/dev_durable_reports.rs` exercise storage, the session kernel and host timers. Usable only by an embedder writing code against it. |
| JS extension (`import "@earendil-works/pi-durable"`) | Storage, `createSession`, `ExecutionEnv`, `/tools`, `/codemode` are ported and importable. **But `Harness`, `createRegistry` and `watchEvents` throw `ERR_NOT_SUPPORTED`** (`extensions/api/shims.rs:128-130`): the scheduler engine is an open decision (upstream's "D5"), not written. |
| The agent loop itself | **Nothing.** `crates/pir-core/src/lib.rs:146-147` re-exports the crate behind `feature = "durable"`, and that is the only `durable::` identifier in the engine — no `TaskScheduler`, no harness, no goal object. `foreman`'s "durable state" is its own journal, unrelated to this crate. |

So the correct statement is not "the runtime has no caller" — it is
**the runtime has no *scheduler-facing* caller, on either side.** The Rust
half has a scheduler nobody in the engine invokes; the JS half exposes the
types but throws on the one entry point that would run them. Both ends stop
at the same seam, which is why connecting it (Track B) is one job, not two.

That is the 0.3.4 thesis in one line: **the storage, session and timer layers
of long-horizon autonomy are already written and tested; the piece that
drives them towards a goal is the piece missing on both sides.**

**Genuinely missing for AGI-shaped behaviour:**

1. **No persistent goal.** A prompt is a single run; there is no object
   that says "this goal is unfinished" and survives a crash, a restart or
   a new session. `--continue` resumes a transcript, not an intention.
2. **No budget accounting across goals.** Turn caps are per-prompt
   (`DEFAULT_AGENT_MAX_TURNS = 1000`, `INTERACTIVE_AGENT_MAX_TURNS = 100`);
   token budgets are per-profile. A goal that takes three prompts restarts
   the count.
3. **No self-critique pass.** The "final self-check" is a prompt sentence,
   not a mechanism; `efficient` even drops that sentence.
4. **No progress signal.** The repeat guard detects *stagnation* by
   identical-call hashing, but nothing measures whether the goal moved.
5. **No scheduled continuation.** Nothing says "come back in 10 minutes
   and check the build". `jobs` and `foreman` detach *processes*, which is
   a different (and heavier) thing. Durable's `Timers` can already do this;
   nothing schedules through it.

## 3. Ease of use: the first five minutes are the worst part

Two concrete defects, both reproducible on a fresh agent dir with no keys:

**Defect A — the first-run wizard never asks for a model.**
`config/first_run.rs:106-160` asks for a theme and analytics consent. It
never mentions a provider or an API key. And the wizard only runs when
`PI_EXPERIMENTAL=1` (`first_run.rs:64-71`), so for a normal install it does
not run at all. A new user's first command therefore hits:

```
Error: no model available; configure a provider with `pir auth login` or
C:\...\.pi\agent\models.json
```

(`coding_agent/overrides.rs:57-64`). That message is accurate and names two
real escape hatches, but it assumes the reader already knows what a
provider, a base URL and a model id are.

**Defect B — `pir auth` is a 54-line wall, not a chooser.**
`pir auth` on a fresh dir prints 9 OAuth providers and ~25 API-key
providers, every one "unset". It is a status dump. There is no ranked
"the three that work in one command" view, no detection of an existing
`OPENAI_API_KEY`-equivalent already in the environment, and no single
command that takes a key and produces a working session.

Neither defect is about *missing features* — everything needed exists
(`auth login`, `models.json`, the provider catalog). Both are about the
**first five minutes** having no designed path through that surface.

## 5. The plan (ordered; each item names how it is accepted)

Three tracks, deliberately ordered so a milestone can ship without the
next one landing. Every item states an **acceptance check** that is a
command or a measurement, not an opinion — the point of §1 is that this
project already has the wrong kind of "light" claims and does not need
more.

### Milestone 0.3.4-A — make "light" a measured profile (no behaviour change)

| # | Work | Acceptance |
|---|---|---|
| A1 | Add a `pir-light` binary: `cli,tools,grep-find,session,skills` + `provider-openai`, **no** `extensions`/`context-mode`/`mcp`/`memory`/`tui`/`durable`. Same shape as the existing `[[bin]] name = "pir-minimal"` (`Cargo.toml:102-105`). | `cargo build --no-default-features --features cli,tools,grep-find,session,skills,provider-openai --release --bin pir-light` succeeds; `pir-light --version` runs; the binary is built **without** QuickJS (assert no `rquickjs` in `cargo tree` for that feature set). |
| A2 | Measure it the way §1.1 measures the other two, and record the row. | Four numbers in `FEATURES.md` §4: binary MiB, unique package count, first-turn request bytes (from a capture, like §1.1), warm startup ms. Must land **between** the minimal and full rows, and the doc must state which artifact each number is from. |
| A3 | Add the feature set as a `feature_matrix.sh` row so it cannot rot. | `bash scripts/feature_matrix.sh` reports the new row and its count assertion is bumped in the same commit. |
| A4 | **Deferred, needs your call:** change the *default* tool set from 12 to 4 + `tool_search`. | Not in 0.3.4 unless you decide it. The cost is measured (§1.1); the benefit is unmeasured at N>1 (`RESULTS.md` is N=1). See §7 Q1. |

A1–A3 are pure addition: no existing binary, feature or default changes.
That is why they can ship even if nothing else in this plan does.

### Milestone 0.3.4-B — give the agent a goal (the actual "AGI" work)

The seam is one function on each side (§2): the Rust scheduler has no
caller, the JS `Harness` throws. Pick the Rust side — it needs no
JavaScript engine, which keeps Track A's win intact.

| # | Work | Acceptance |
|---|---|---|
| B1 | Define the **goal** type in `pir-durable`: id, phases, budget (turns + tokens), checkpoint, status. Reuse `TaskDefinition`/`define_task` (`crates/pir-durable/src/tasks.rs:19,69`) rather than a new abstraction. | A unit test opens a goal, records two phases, reloads it from storage, and sees both phases — no engine involved. |
| B2 | Drive it from the engine: a goal run calls the existing `agent_loop` per phase and persists the phase result through the goal. | An integration test in `tests/` runs a two-phase goal against the mock provider and asserts **both** phases ran and the budget was debited **once across both** — this is the fix for missing-item 2. |
| B3 | Make the budget survive a restart: kill and reopen the process mid-goal, resume from the checkpoint. | A test that writes a goal, drops the handle, reopens from disk, and continues — asserting the turn counter did **not** reset (missing-item 1). |
| B4 | Scheduled continuation through the existing `Timers` (`crates/pir-durable/src/timers.rs:162`), not `jobs`/`foreman`. | A test with an injected clock (the durable timers take host timers, `timers.rs:207`) that fires a continuation and asserts the goal advanced with no process detached. |

B1–B3 are the milestone. B4 is the piece that makes it "AGI-shaped" rather
than "resumable", and it is explicitly allowed to slip to 0.3.5 if the
clock injection fights the engine's tokio time.

> B2's test is the one that decides whether this track was worth it: if a
> two-phase goal cannot share one budget without editing `agent_loop`,
> then the "second harness" caveat in `durable-spec.md:18` is real and
> this plan is wrong. Find that out with B1+B2, before B3/B4.

### Milestone 0.3.4-D — size the task and pick the mode that guarantees it

Today the mode is a **user** decision (`/mode normal|foreman|plan`,
`pir-core/src/plugins/builtin/mode/mod.rs:1891`), and the three modes do
not offer the same correctness — they offer different *kinds* of it:

| mode | correctness mechanism | where |
|---|---|---|
| `normal` | **none.** A tool error is a result, the loop continues; a run that stops early is still a run. | — |
| `plan` | **execution contract**: the approved plan is not done until a real verification command exits 0; a claim of "verified" does not count. 3 reminder budget, then the run is marked UNVERIFIED. | `VERIFICATION_GATE_MESSAGE`, `mod.rs:147` |
| `foreman` | **independent reviewer**: no worker counts as delivered until a `reviewer` subagent replies `{"verdict":"PASS"}`; an errored/aborted/`length` worker is a failure the gate rejects even if a reviewer says PASS. 3 nudges, then UNVERIFIED. | `GATE_MESSAGE`, `mod.rs:137`; `is_failed` (`pir-builtin-subagent/src/lib.rs:571`) treats `length` as failure |

So "small, medium and large tasks all execute correctly by themselves" is
**not** a routing problem — routing a task to `normal` is fast and gives
*no* correctness guarantee at all. The requirement is two things:

1. **size the task**, and
2. **guarantee its completion** at that size — which means the smallest
   lane needs a verification mechanism it does not have today.

| # | Work | Acceptance |
|---|---|---|
| D1 | **A verification floor for every lane**, independent of mode. The cheapest general one is the `plan` contract's shape: a run is not complete until one declared check exits 0. Give `normal` the same settle check, applied to the task the goal recorded. | A test drives a `normal` run whose model claims success while its declared check fails, and asserts the run is **not** reported complete and is nudged to fix it. This is the item that makes "small tasks execute correctly" true rather than hoped for. |
| D2 | **A task sizing signal**, computed before the first turn: does the request touch >N files / need a plan / already failed once? Use measurable inputs only (paths named in the prompt, repo size, whether the previous attempt failed), never a model self-assessment. | A table test over recorded `RESULTS.md`-style task fixtures (the `s1`/`s2`/`l1`/`c3` shapes already used there) where the expected lane is written down, so sizing is a **regression-tested function**, not a heuristic nobody checks. |
| D3 | **Auto mode selection** from D2's signal, with the lane's guarantee attached: small → the new verified-`normal` lane, medium → `plan`, large → `foreman`. Record the chosen lane and the reason in the goal (B1), so a wrong guess is visible and resumable. | A run started with no `/mode` command reports its chosen lane and reason, and switching lanes mid-run is refused with a reason instead of silently changing the guarantee. |
| D4 | **Escalation on failure, never on vibes**: a lane that fails its own check twice escalates one size up (verified-`normal` → `plan` → `foreman`), recording each escalation in the goal. De-escalation does **not** happen automatically. | A test where the first lane fails twice and the run ends in the next lane, with both attempts and both verdicts in the goal's ledger. |

**Order is D1 → D2 → D3 → D4**, and D1 is not optional: without it, D3
would route small tasks into the one lane that cannot tell success from
failure. **D1 alone is already an improvement** (every `normal` run gains
a verification floor) and ships independently of B.

> Deliberate non-goal: D2 must not ask the model "how hard is this?".
> A self-assessment is unmeasurable, and §1's whole method is that claims
> become numbers or they do not go in the plan. Sizing uses inputs the
> harness already has.

### Milestone 0.3.4-C — the first five minutes

| # | Work | Acceptance |
|---|---|---|
| C1 | Setup asks for a model. Detect an already-set key (the same list `pir auth` prints) and offer it as the default answer instead of asking for a raw string. | On a fresh agent dir with `OPENAI_API_KEY` set and `PI_EXPERIMENTAL=1`, setup ends with a `settings.json` that a subsequent `pir -p "hi"` uses **without** the `no model available` error. |
| C2 | `pir auth` with nothing configured becomes a chooser (3 ranked options → working session); the 54-line dump moves to `pir auth status`. | `pir auth` on a fresh dir prints ≤ 12 lines and every option ends in a runnable command; `pir auth status` prints what today's `pir auth` prints. |
| C3 | **Deferred:** bucket the 67 settings keys into 6 + advanced. | Not in 0.3.4 — it touches the schema, the settings menu and every doc that lists keys. Proposed for 0.3.5 with its own plan. |

C1 and C2 are independent of A and B and can ship in any order.

### Suggested release shape

Since the theme is B (a goal), the order that keeps the theme intact:

1. **B1 + B2** first — they answer the only question that can invalidate
   the whole direction (see the B2 note). If they fail, stop and we
   re-plan around what B2's test proved.
2. **D1** next, before any of D2–D4 — it is the item that turns "small
   tasks execute correctly" from a hope into a tested property, and it
   improves every `normal` run even if D2–D4 never land.
3. **B3, D2, D3** — persistence, sizing, routing.
4. **B4, D4, C1, C2** — scheduled continuation, escalation, first-run.

**A** (the `pir-light` binary) is independent of all of it and can ride
along in any release that has room; it is the only item whose acceptance
is a pure measurement. If 0.3.4 has to ship while B is still in progress,
ship A + C1/C2 and leave the theme to 0.3.5 rather than shipping a
half-connected goal.

## 6. What must NOT change

- **Production run speed and TUI hard contracts.** 0.3.3's release was
  blocked once by a retry budget that regressed empty-file `open` from 26 ms
  to 596 ms; that class of "correct but slower" change is out.
- **Extracted crates stay independent** (`tests/version_consistency.rs`
  enforces it). Track B connects durable *as a consumer*, never by taking a
  dependency edge back into the engine.
- **No new runtime.** Track B uses the QuickJS-free durable runtime; adding
  a second interpreter to reach "AGI" would trade the one measurable win
  ("light") for the thing users cannot see.

## 7. Decisions (settled here) and the one that needs you

**Settled, with the reason:**

1. **`pir-light` is a second binary, like `pir-minimal`.** A smaller default
   feature set on the *same* `pir` binary would be a lie about size: the
   published `pir` is built with `default = ["full"]`, so the `crates.io`
   install keeps its 73 MiB regardless. A second `[[bin]]` is the only
   artifact whose weight can be *measured and attributed* (acceptance A2),
   and `pir-minimal` already established that pattern
   (`Cargo.toml:102-105`). Cost: a second install name, accepted.
2. **A goal is its own store, keyed alongside a session.** `--continue`
   users will expect resumption to follow the transcript, so the goal
   records the session id it advances; but the goal itself is not a
   message in the transcript, because a goal outlives one transcript and
   must be openable with no session at all (B3's test reopens it from
   disk). Storing it *as* session entries would force the two lifecycles
   to be equal, which is exactly the constraint missing-item 1 describes.

**Needs your call (blocks A4 only, not the rest of the plan):**

**Should the default tool set drop from 12 to 4 + `tool_search`?**

It is a product decision, not an engineering one, and I am not going to
make it for you:

- **Measured:** 12 tools cost 15,670 B of `tools[]` on **every** turn;
  4 tools + `tool_search` would cost roughly a third of that (§1.1's
  15,670 B is dominated by the eight non-core declarations).
- **Unmeasured:** whether models actually call `tool_search` instead of
  asking for what they need. `RESULTS.md` has one measured observation
  (`ctx_*` called zero times across six runs) that supports *removing*
  tools nobody calls, but none that supports *hiding* tools the model
  must first discover. That is the risk.
- **My recommendation:** ship A1–A3 first (they don't touch the default),
  then run a small N>1 A/B on this specific question before changing what
  a new user gets. Changing the default without that evidence would
  repeat the mistake §1 exists to correct.

Everything else in §5 has an acceptance check that does not depend on this
answer.
