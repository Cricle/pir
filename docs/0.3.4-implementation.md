# 0.3.4 implementation plan — a goal-driven agent with a correctness floor

Companion to [`0.3.4-plan.md`](0.3.4-plan.md), which states *what* and *why*.
This document states *how*: data shapes, call paths, file-level touch list,
failure modes, and test fixtures. Every `file:line` was read on this tree.

Read order: §1 (the two seams) explains why every item below is a small,
local change rather than a rewrite. §2–§5 are the four milestones. §6 lists
what each item must not break.

---

## 1. The two seams that make this tractable

Both milestones attach to machinery that already exists and is already
tested. Neither requires a new runtime, a new storage format or a new loop.

### Seam 1 — durable already has a task scheduler with phases and timers

| need | existing API | location |
|---|---|---|
| phase handlers | `PhaseHandler`, `phase_handler(...)` | `harness/task.rs:64,72` |
| executable task definition | `generation_task(...) -> Task` (the "run an agent" example) | `harness/generation.rs:584` |
| the runner's toolbox | `TaskRuntime::{commit, sleep_until, set_timer, create_task, outcomes, report}` | `harness/scheduler/runtime.rs:234,281,348,433,390,198` |
| the host | `Harness::open(HarnessOptions{..})`, `HarnessOptions{tasks, timers, now, ..}` | `harness/harness.rs:1412`, `:210-268` |
| task catalogue | `TaskCatalogue`, `CatalogueHandle` | `scheduler/mod.rs:165,259` |

`HarnessOptions.tasks` is precisely where a goal task plugs in. There is no
"add a scheduler" step: the scheduler is the thing that will call us.

### Seam 2 — the correctness gate is already installed on Normal

The gate lives in `plugins/builtin/mode/mod.rs:1080-1131`
(`contract_gate_continuation`), which calls `verification_evidence_passed`
(`mod.rs:2173`), and it is dispatched from `gate_continuation`
(`mod.rs:999-1008`):

```rust
if mode == Mode::Foreman { return self.foreman_gate_continuation(payload); }
if mode == Mode::Normal  { return self.contract_gate_continuation(payload); }
None    // Plan
```

Two properties of that code are the whole reason D is cheap:

1. **It matches a specific declared command, not a claim.** The model must
   actually run `bash` with the exact declared string.
2. **Evidence only counts after the last mutation** (`mod.rs:2183-2188`:
   `last_mutation`). Verifying and then editing is rejected. This is the
   anti-pattern D1 must inherit or it will be worthless.

**Where the gate actually applies** (this was mis-stated in an earlier
revision as "plan mode has it, normal does not" — the opposite is true):

- `Plan` mode is read-only planning and **never gates a run** (`None` above).
  On approval the plugin switches the session back to Normal so the contract
  governs execution: `mod.rs:2959-2966`
  (`apply_mode_with_notice(state, Mode::Normal, "... the verification
  contract is active")`).
- The gate therefore fires on **Normal** runs that carry a contract. It is
  invisible in a plain `normal` run only because `active_contract()` returns
  `None` at the first `?` (`mod.rs:1081`).

What is missing is not a mechanism and not even a dispatch arm — it is that
`active_contract()` has exactly one producer, `set_active_contract` called
from plan approval (`mod.rs:2950`). D1 gives it a second producer: the goal's
checks.

## 2. Milestone B — the goal

### 2.1 The data shape

A goal is a durable task, not a new storage format. Reuse
`TaskDefinition`/`define_task` (`crates/pir-durable/src/tasks.rs:19,69`):

```rust
// crates/pir-durable/src/harness/goal.rs  (new module)

/// What a goal is trying to achieve, independent of any one phase.
pub struct GoalSpec {
    pub objective: String,
    /// Ordered phases. Each runs one or more agent turns.
    pub phases: Vec<GoalPhase>,
    /// The budget the WHOLE goal draws from, not each phase.
    pub budget: GoalBudget,
    /// Declared checks that must exit 0 before the goal may report success.
    pub checks: Vec<CheckSpec>,
}

pub struct GoalPhase {
    pub name: String,
    /// The instruction this phase hands the agent loop.
    pub instruction: String,
    /// Which lane's guarantee applies (filled by D3; `Lane::Verified` until then).
    pub lane: Lane,
}

pub struct GoalBudget {
    pub max_turns: u64,      // counted across ALL phases
    pub max_tokens: u64,     // summed across ALL phases
}

pub struct CheckSpec {
    /// The exact command string an agent must run (matched verbatim, like the
    /// plan contract). Not a regex, not a description.
    pub command: String,
    /// Working directory the command must run in.
    pub cwd: String,
}
```

The three lifecycle items the research note called missing map onto fields
that already exist in `TaskRecord`:

| missing item | how the goal fixes it |
|---|---|
| 1. no persistent goal | the goal **is** a `TaskRecord`; storage already reopens it (`Harness::open` on the same dir) |
| 2. no cross-prompt budget | `GoalBudget` lives in the task's checkpoint and is debited by every phase through one counter |
| 5. no scheduled continuation | `TaskRuntime::set_timer` / `sleep_until` — no `jobs`, no detached process |

### 2.2 The task definition

Modelled directly on `generation_task` (`harness/generation.rs:584`), which
already shows the pattern: build a `TaskDefinition` whose phases are
`PhaseHandler`s, erase it behind `Task`.

```
phases: plan -> execute -> verify -> (rework -> verify)* -> done
                     ^                        |
                     +------------------------+
```

| phase | handler does | commits |
|---|---|---|
| `plan` | asks the agent for the phase list (or uses `GoalSpec.phases` verbatim when given) | the plan |
| `execute` | runs `agent_loop` for one phase's instruction with the **remaining** budget | phase output + **budget debit** |
| `verify` | runs each `CheckSpec` through the same evidence matcher the plan gate uses, requiring the run to be **after** the last mutation | verdict + evidence call id |
| `rework` | re-instructs with the verifier's failure text, returns to `verify` (bounded) | attempt count |
| `done` | records terminal status `VERIFIED` / `UNVERIFIED` | final |

Every commit goes through `TaskRuntime::commit` (`runtime.rs:234`), which
lands as one commit on the session line — so a crash mid-goal resumes at the
last committed phase, which is B3 for free.

### 2.3 The engine side (the only real work)

The goal task needs to call the engine's `agent_loop`. Today `pir-durable`
**must not** depend on `pir-core`: the gate at
`tests/version_consistency.rs:375` (`extracted_crates_never_depend_on_the_engine`)
skips only `pir-core`, `pir-sdk` and `ENGINE_DEPENDENT_BY_DESIGN` — and
`pir-durable` is in none of those. So a normal `pir-durable → pir-core`
dependency would fail that test, and a dev-dependency would not help
(the gate ignores dev-deps, but the production code needs it).

The call therefore goes through a trait the **host** supplies — which is
already this crate's idiom: `HarnessOptions` supplies `registry`,
`settings`, `timers`, `now` and `on_report` the same way
(`harness/harness.rs:211-268`). Adding `runner` beside them is consistent
with the existing seam, not a workaround:

```rust
// declared in pir-durable, implemented in pir-core
pub trait GoalRunner: Send + Sync {
    /// Run one phase's instruction against the agent, drawing on `budget`.
    /// Returns what the phase produced and what it spent.
    fn run_phase<'a>(
        &'a self,
        phase: &'a GoalPhase,
        budget: &'a GoalBudget,
        context: Context,
    ) -> BoxFuture<'a, Result<PhaseOutcome>>;
}
```

`pir-core` implements it with a thin wrapper over
`AgentSession::prompt_with_events` (the same call `minimal.rs:158-164` uses),
passing the remaining budget as `LoopDeps::max_turns` and accumulating usage
from the returned `AssistantMessage`. **No change to `agent_loop` itself** —
which is exactly what B2's acceptance test is designed to detect the absence
of.

### 2.4 B2's test is the go/no-go

Write this test **first**, before the rest of B. It is:

```
tests/goal_budget_spans_phases.rs
  - open a Harness over a temp dir with a goal task installed
  - install a GoalRunner whose run_phase records the budget it was handed
  - drive plan -> execute -> execute (two phases)
  - assert phase 2's budget == phase 1's budget minus phase 1's spend
  - assert the total across both never exceeded GoalBudget
```

If this test cannot be written without reaching into `agent_loop`'s
internals, **stop**: the "second harness" warning in
`docs/durable-spec.md:18` is real, and the plan should switch to putting the
goal *inside* the agent loop (a much larger change) with that knowledge in
hand. Find this out in days, not weeks.

## 3. Milestone D — size the task, guarantee the lane

### 3.1 D1: a verification floor for every lane

The floor is: **a run that declares checks is not complete until one check's
successful evidence exists after the last mutation.**

Reuse, do not reimplement:

| piece | reuse from | note |
|---|---|---|
| evidence matching | `verification_evidence_passed`, `mod.rs:2173` | already handles the `last_mutation` ordering |
| bounded nudging | `gate_nudge`, `mod.rs:1133` | one budget, capped below the host's continuation cap |
| the gate hook | `contract_gate_continuation`, `mod.rs:1080` | already returns `Some(Value)` to continue the run |

The change is: today the only producer of a contract is plan approval
(`set_active_contract`, called at `mod.rs:2950`). D1 gives it a second
producer — the goal's checks — by making the accessor fall back:

```
active_contract()  ->  explicit plan contract, else
                       goal contract (from B's checkpoint), else
                       None
```

**Two traps that make this more than a one-line fallback** (found by reading
the gate's own code, and both would ship a broken gate if missed):

1. **`evidence_baseline` must be computed, not left `None`.** The field is
   documented to *fail closed* when `None` (`pir-builtin-mode/src/journal.rs:86-91`):
   "`None` (host could not enumerate the transcript) makes the gate fail
   closed rather than accept unknown history." A synthesised goal contract
   that leaves it `None` would nudge every run to the 3-nudge limit and mark
   it UNVERIFIED no matter what the model does. The producer must call
   `shell_call_baseline(&context)` (`mod.rs:2898`) at the same moment plan
   approval does — i.e. **before the phase's first turn**, so pre-existing
   shell calls cannot satisfy the goal's checks.
2. **`set_active_contract` resets the pass markers** (`mod.rs:602-609`
   clears `verification_passed_id` and `verified_call`). The goal fallback
   must not call it on every read, or a contract that was just satisfied is
   re-armed and the run never settles. Fall back in the *getter*, install
   once.

So the change is one producer plus one getter branch — still small, but the
"~15 lines" in an earlier revision was optimistic and, worse, would have
been correct-looking and broken at runtime. Revised estimate: **one new
function (~25 lines) + a getter branch (~8 lines) + the baseline wiring**.

Accepting:

```
tests/verification_floor_normal.rs
  - normal lane, goal with one check
  - mock model claims done without running the check  -> run is NOT complete,
    one nudge, run continues
  - mock model runs the check, then makes another edit, then claims done
    -> still NOT complete (the last_mutation ordering)
  - mock model runs the check last                                -> complete
  - a check that was already run BEFORE the goal started does not count
    (the evidence_baseline case)
  - after the run completes, a second settle does not re-arm the gate
    (the set_active_contract reset case)
```

The fourth case is the one that catches a naive implementation (free, because
`verification_evidence_passed` already implements it); the fifth and sixth
catch the two traps above.

### 3.2 D2: sizing from inputs the harness already has

The signal must be **a pure function of observable inputs**, so it can be a
regression test. Inputs available before turn one:

| input | source |
|---|---|
| files named in the prompt | existing `@file` parsing |
| repo size / touched-module count | a `find` over the cwd, bounded |
| previous attempt in this goal | B's checkpoint (the attempt ledger) |
| does the prompt already contain a multi-step instruction | token count + conjunction heuristics (measurable, not a model call) |

Signature:

```rust
pub fn size_task(input: &TaskInputs) -> Sized {
    // -> Small | Medium | Large, each with a `reason: &'static str` for the
    // goal ledger (D3 records it; a wrong guess must be explainable)
}
```

The regression fixture already exists — `RESULTS.md:179-181,209-212` records
`s1-duration`, `s2-slugify` (short), `l1-ledger`, `c3-two-turn` (long) with
measured token counts. Write the table test **against those**, so the
function is pinned to real tasks rather than invented ones.

**Non-goal, restated:** never ask the model to rate difficulty. That is
unmeasurable and it is the one thing §1 of the companion doc argues against.

### 3.3 D3: auto lane selection

```
Small  -> Verified      (normal's speed + D1's floor)
Medium -> Plan          (plan's execution contract)
Large  -> Foreman       (independent reviewer)
```

- selection happens once, before turn one, and the result is written into the
  goal (phase name, lane, reason)
- a mid-run `/mode` that contradicts the chosen lane is **refused** with the
  recorded reason rather than silently changing the guarantee
- accepting: a run started with no `/mode` reports its lane and reason, and
  the lane's guarantee is observably active (D1's floor for Small, the
  contract for Medium, the reviewer gate for Large)

### 3.4 D4: escalation only

```
attempt 1 fails check -> rework within the same lane
attempt 2 fails check -> escalate one lane up, record it
never de-escalate automatically
```

Escalation is written to the goal ledger as a `JournalEvent`-shaped record
(reuse the shape at `pir-builtin-mode/src/journal.rs:406`), so the history is
auditable and a resumed goal knows which lane it is on.

## 4. Milestone A — `pir-light` (independent, ship any time)

Additive only:

```toml
[[bin]]
name = "pir-light"
path = "src/bin/pir_light.rs"
required-features = ["cli", "tools", "grep-find", "session", "skills", "provider-openai"]
```

No existing binary, feature or default changes. Acceptance is the four
measurements from the companion doc §1.1, recorded in `FEATURES.md` §4, plus
a `feature_matrix.sh` row.

**Open risk to check first:** `pir-core`'s `full` closure may pull heavy
crates unconditionally. **Checked on this tree — it does not:**

```
cargo tree --no-default-features \
  --features cli,tools,grep-find,session,skills,provider-openai -p pir-core \
  | grep -E "rquickjs|swc|rusqlite|rmcp"
```

returns **nothing** (only `ciborium` appears, via the unconditional
`pir-protocol`). The feature gates are clean, and the same feature set
resolves **186 unique packages** — between minimal's **149** and full's
**436**, all counted the same way (`cargo tree -p pir-sdk … -e normal
--target x86_64-pc-windows-gnu`, unique names). So A is genuinely a
`[[bin]]` + a measurement, not a gating project. If a future change leaks
one of those four into the closure, this grep is the check that catches it.

**What the light set does NOT drop, and why that is the real finding.**
Measured additively from the light base, the heavy carriers are:

| feature | packages added over light |
|---|---:|
| `mcp` (incl. the `extensions` it depends on) | +130 |
| `extensions` (QuickJS + SWC) | +104 |
| **`brush`** | **+93** |
| `tui` | +41 |
| `image-tools` | +20 |

An earlier revision of the companion doc said "two carriers, everything else
is rounding"; that was wrong (see its §1.2 correction). The consequence for
A is that **186 packages is a genuinely different product**, not a slightly
trimmed `full`.

**Decision: `pir-light` ships WITHOUT `brush`, and `pir` keeps it.**

This was measured rather than assumed. brush is the embedded
bash-compatible shell behind `pir __brush` (`shell_embed/mod.rs:1-10`), and
its position in the resolution order is **last-resort fallback, never
preferred**:

```
Windows: shellPath -> Git Bash candidate paths -> bash.exe on PATH -> brush -> error
Unix:    /bin/bash -> bash on PATH -> brush -> sh
```
(`coding_agent/tools/bash.rs:936-941`, `:949-958`)

`shell_pool.rs:2283` does not add a second path: it only reuses brush when
`program` is *already* the embedded one, i.e. it mirrors that fallback.

That makes the value split sharply by user:

| user | what brush buys |
|---|---|
| Linux / macOS | **nothing.** `/bin/bash` exists, so the fallback is never reached. 93 packages of pure weight. |
| Windows **with** Git Bash (the common dev setup) | **nothing.** Same reason. |
| Windows **without** any bash | **everything.** Without brush the `bash` tool fails hard with "No bash shell found. Install Git for Windows…". With it, the tool works. |

So brush is not redundant — it is the only thing that makes Windows
work out of the box. But that is a **first-run guarantee**, not a daily
benefit, and it belongs to the binary whose job is "install and it works".

Hence the split:

- **`pir`** (the shipped default) keeps `brush`. Anyone who installs it can
  use the `bash` tool on a machine with no bash installed. That guarantee is
  the reason the feature exists.
- **`pir-light`** omits it — and the specified feature list already does:
  `cargo tree … --features cli,tools,grep-find,session,skills,provider-openai`
  contains **zero** `brush` packages. So the 186 above is *already* the
  brush-free figure; adding brush to that set takes it to 279 (+93, i.e.
  half again). The decision is therefore not "remove something" but "state
  it and lock it": add an assertion so a future feature cannot quietly pull
  brush back in.
- **The cost of the split is stated, not hidden:** a Windows user with no
  bash who installs `pir-light` gets the old hard error. That is acceptable
  for a profile that trades convenience for size by definition, and the
  error text already tells them exactly what to install.

Capability checked before deciding (brush was run, not read about): pipes,
loops, command substitution, `$?` propagation, redirection, heredoc,
functions, `set -e`, PATH inheritance and **invoking external programs**
(`git rev-parse`, `rustc --version`) all work. A backslash path is eaten
(`crates\pir-core\src\x.rs` → `cratespir-coresrcx.rs`), but **real bash
behaves identically**, so that is POSIX semantics rather than a brush defect.

## 6. Touch list and blast radius

| area | files | risk |
|---|---|---|
| goal task | `crates/pir-durable/src/harness/goal.rs` (new), `harness/mod.rs` export | contained; new module |
| engine adapter | `crates/pir-core/src/plugins/builtin/goal.rs` (new), implementing `GoalRunner` | contained; new module |
| verification floor | `plugins/builtin/mode/mod.rs` (`active_contract`), ~15 lines | **medium** — it changes when `normal` runs may finish |
| sizing | `crates/pir-builtin-mode/src/size.rs` (new, engine-free) | low; pure function |
| lane select | `plugins/builtin/mode/mod.rs` (selection + refusal) | **medium** — it changes mode semantics |
| light binary | `Cargo.toml`, `src/bin/pir_light.rs` | low; additive |
| first-run | `config/first_run.rs`, `cli.rs` auth arm | low |

**Must not break** (each has an existing test or a hard contract):

- production run speed and TUI contracts — the 0.3.3 release was blocked once
  by a retry budget that made empty-file `open` 596 ms instead of 26 ms
- `extracted_crates_never_depend_on_the_engine` — the `GoalRunner` trait
  exists precisely so durable never imports the engine
- `pir-native-shell` stays unpublished; extracted builtins stay independent
- tests live in `tests/`, never in `src`

## 7. Order, and what each step buys

| step | buys | if it fails |
|---|---|---|
| B2 test | proof the goal can drive the loop without touching it | stop; re-plan with the proof in hand |
| B1 | a persistent goal object that reopens from disk | still useful as a library |
| B3 | crash-resumable goals | falls back to B1 |
| D1 | **every** `normal` run gains a correctness floor | ship without D2–D4 |
| D2 | sizing becomes a regression-tested function | D3 falls back to "always Medium" |
| D3 | automatic lane selection | users keep choosing `/mode` manually |
| D4 | failure escalates instead of silently finishing | lane stays where it started |
| A | a measurable "light" artifact | nothing else is affected |
| C1/C2 | a first five minutes with a path through it | nothing else is affected |

D1 is the highest value per line changed in this whole document: ~15 lines
at one seam, and it is the item that makes "small tasks execute correctly"
a property rather than a hope.
