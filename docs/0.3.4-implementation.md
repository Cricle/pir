# 0.3.4 implementation plan — a correctness floor, durable-backed tasks, the right lane

Companion to [`0.3.4-plan.md`](0.3.4-plan.md), which states *what* and *why*.
This document states *how*: data shapes, call paths, file-level touch list,
failure modes, and test fixtures. Every `file:line` was read on this tree.

Read order: §1 (the two seams) explains why every item below is a small,
local change rather than a rewrite. §2–§4 are the three milestones. §5 lists
what each item puts at risk, §6 what each one buys and in what order.

A note on what is measurable vs deferred: D1, D2a, D3's two lanes, D5 and C1/C2
are ships-now work with no dependency on the task record. Everything in §2
(durable) and D2b/D4/D3-medium depends on B2's go/no-go. The order table in
§6 makes that split explicit rather than interleaving the two.

---

## 1. The two seams that make this tractable

Both seams attach to machinery that already exists and is already tested.
Neither requires a new runtime, a new storage format or a new loop. Seam 2 is
what makes D1 the first item on the order table rather than the last: the
gate is already wired, so D1 only has to feed it.

### Seam 1 — durable already has a task scheduler with phases and timers

| need | existing API | location |
|---|---|---|
| phase handlers | `PhaseHandler`, `phase_handler(...)` | `harness/task.rs:64,72` |
| executable task definition | `generation_task(...) -> Task` (the "run an agent" example) | `harness/generation.rs:584` |
| the runner's toolbox | `TaskRuntime::{commit, sleep_until, set_timer, create_task, outcomes, report}` | `harness/scheduler/runtime.rs:234,281,348,433,390,198` |
| the host | `Harness::open(HarnessOptions{..})`, `HarnessOptions{tasks, timers, now, ..}` | `harness/harness.rs:1412`, `:210-268` |
| task catalogue | `TaskCatalogue`, `CatalogueHandle` | `scheduler/mod.rs:165,259` |

`HarnessOptions.tasks` is precisely where a durable task plugs in. There is no
"add a scheduler" step: the scheduler is the thing that will call us.

### Seam 2 — the correctness gate is already installed on Normal

The gate lives in `plugins/builtin/mode/mod.rs:1080-1131`
(`contract_gate_continuation`), which calls `verification_evidence_passed`
(`mod.rs:2173`), and it is dispatched from `gate_continuation`
(`mod.rs:999-1008`):

```rust
if mode == Mode::Foreman { return self.foreman_gate_continuation(payload); }
if mode == Mode::Normal  { return self.contract_gate_continuation(payload); }
None    // Plan
```

Two properties of that code are the whole reason D is cheap:

1. **It matches a specific declared command, not a claim.** The model must
   actually run `bash` with the exact declared string.
2. **Evidence only counts after the last mutation** (`mod.rs:2183-2188`:
   `last_mutation`). Verifying and then editing is rejected. This is the
   anti-pattern D1 must inherit or it will be worthless.

**Where the gate actually applies** (this was mis-stated in an earlier
revision as "plan mode has it, normal does not" — the opposite is true):

- `Plan` mode is read-only planning and **never gates a run** (`None` above).
  On approval the plugin switches the session back to Normal so the contract
  governs execution: `mod.rs:2959-2966`
  (`apply_mode_with_notice(state, Mode::Normal, "... the verification
  contract is active")`).
- The gate therefore fires on **Normal** runs that carry a contract. It is
  invisible in a plain `normal` run only because `active_contract()` returns
  `None` at the first `?` (`mod.rs:1081`).

What is missing is not a mechanism and not even a dispatch arm — it is that
`active_contract()` has exactly one producer, `set_active_contract` called
from plan approval (`mod.rs:2950`). D1 gives it two more: a declared `--check`
command (ships without B) and the task record's checks (after B). §3.1 turns
"two more producers" into the concrete list, including the three traps that
make the getter branch non-trivial.

## 2. Milestone B — the durable task record

### 2.1 The data shape

A task record is a durable task, not a new storage format. Reuse
`TaskDefinition`/`define_task` (`crates/pir-durable/src/tasks.rs:19,69`):

```rust
// crates/pir-durable/src/harness/task_record.rs  (new module)

/// What a task is trying to achieve, independent of any one phase.
pub struct TaskSpec {
    pub objective: String,
    /// Ordered phases. Each runs one or more agent turns.
    pub phases: Vec<TaskPhase>,
    /// The budget the WHOLE task draws from, not each phase.
    pub budget: TaskBudget,
    /// Declared checks that must exit 0 before the task may report success.
    pub checks: Vec<CheckSpec>,
}

pub struct TaskPhase {
    pub name: String,
    /// The instruction this phase hands the agent loop.
    pub instruction: String,
}

pub struct TaskBudget {
    pub max_turns: u64,      // counted across ALL phases
    pub max_tokens: u64,     // summed across ALL phases
}

pub struct CheckSpec {
    /// The exact command string an agent must run (matched verbatim, like the
    /// plan contract). Not a regex, not a description.
    pub command: String,
    /// Working directory the command must run in.
    pub cwd: String,
}
```

The three lifecycle items the research note called missing map onto fields
that already exist in `TaskRecord`:

| missing item | how the task record fixes it |
|---|---|
| 1. no persistent task | the record **is** a `TaskRecord`; storage already reopens it (`Harness::open` on the same dir) |
| 2. no cross-prompt budget | `TaskBudget` lives in the task's checkpoint and is debited by every phase through one counter |
| 5. no scheduled continuation | `TaskRuntime::set_timer` / `sleep_until` — no `jobs`, no detached process |

**The lane is deliberately not a field here.** `Lane` (`Verified`/`Planned`/
`Reviewed`, §3.3) is the mode plugin's vocabulary, and putting it in this
struct would create a dependency edge that does not exist and may not exist:
`pir-durable` and `pir-builtin-mode` have no edge either way, both are
engine-free, and only `pir-core` depends on both
(`pir-core/Cargo.toml:36,51`). Options that were rejected:

| option | why not |
|---|---|
| `Lane` in `pir-durable` | forces `pir-builtin-mode` (and its `pir-plugin-api` edge) to define the mode plugin's vocabulary, for a field the runtime never reads |
| `Lane` in `pir-builtin-mode` | forces `pir-durable` to depend on a plugin crate — a durability runtime that cannot be used without the mode plugin |
| `Lane` in `pir-plugin-api` | neutral crate, but makes a long-horizon runtime import *plugin* types; `Lane` is a product decision about guarantees, not a plugin-API contract |

Instead, the record keeps the neutral parts — `phases`, `budget`, `checks`,
attempt ledger, status — and the chosen lane is written to the **task ledger**
(a lane name string plus its reason, §3.3), which is data, not a type the
runtime must understand. `pir-core`, which already sees both crates, is the
only place that maps a `TaskSize` to a lane. That is also why §3.3's table
names `Mode::Normal` twice: the lane is a `(mode, floor armed, tool set)`
triple, and the record stores the triple's name, not a union of modes.

### 2.2 The task definition

Modelled directly on `generation_task` (`harness/generation.rs:584`), which
already shows the pattern: build a `TaskDefinition` whose phases are
`PhaseHandler`s, erase it behind `Task`.

```
phases: plan -> execute -> verify -> (rework -> verify)* -> done
                     ^                        |
                     +------------------------+
```

| phase | handler does | commits |
|---|---|---|
| `plan` | asks the agent for the phase list (or uses `TaskSpec.phases` verbatim when given) | the plan |
| `execute` | runs `agent_loop` for one phase's instruction with the **remaining** budget | phase output + **budget debit** |
| `verify` | runs each `CheckSpec` through the same evidence matcher the plan gate uses, requiring the run to be **after** the last mutation | verdict + evidence call id |
| `rework` | re-instructs with the verifier's failure text, returns to `verify` (bounded) | attempt count |
| `done` | records terminal status `VERIFIED` / `UNVERIFIED` | final |

Every commit goes through `TaskRuntime::commit` (`runtime.rs:234`), which
lands as one commit on the session line — so a crash mid-task resumes at the
last committed phase, which is B3 for free.

### 2.3 The engine side (the only real work)

The task record needs to call the engine's `agent_loop`. Today `pir-durable`
**must not** depend on `pir-core`: the gate at
`tests/version_consistency.rs:375` (`extracted_crates_never_depend_on_the_engine`)
skips only `pir-core`, `pir-sdk` and `ENGINE_DEPENDENT_BY_DESIGN` — and
`pir-durable` is in none of those. So a normal `pir-durable → pir-core`
dependency would fail that test, and a dev-dependency would not help
(the gate ignores dev-deps, but the production code needs it).

The call therefore goes through a trait the **host** supplies — which is
already this crate's idiom: `HarnessOptions` supplies `registry`,
`settings`, `timers`, `now` and `on_report` the same way
(`harness/harness.rs:211-268`). Adding `runner` beside them is consistent
with the existing seam, not a workaround:

```rust
// declared in pir-durable, implemented in pir-core
pub trait TaskRunner: Send + Sync {
    /// Run one phase's instruction against the agent, drawing on `budget`.
    /// Returns what the phase produced and what it spent.
    ///
    /// `checks` are the task's declared checks, and they are here rather than
    /// on `TaskPhase` because verification is a per-task need: the phase does
    /// not know which lane it is in, and it does not have to. The runner
    /// (host side, where `Mode` lives) decides what a phase's guarantee is.
    fn run_phase<'a>(
        &'a self,
        phase: &'a TaskPhase,
        budget: &'a TaskBudget,
        checks: &'a [CheckSpec],
        context: Context,
    ) -> BoxFuture<'a, Result<PhaseOutcome>>;
}
```

`pir-core` implements it with a thin wrapper over
`AgentSession::prompt_with_events` (the same call `minimal.rs:158-164` uses),
passing the remaining budget as `LoopDeps::max_turns` and accumulating usage
from the returned `AssistantMessage`. **No change to `agent_loop` itself** —
which is exactly what B2's acceptance test is designed to detect the absence
of.

### 2.4 B2's test is the go/no-go

Write this test **first**, before the rest of B. It is:

```
tests/task_budget_spans_phases.rs
  - open a Harness over a temp dir with a durable task installed
  - install a TaskRunner whose run_phase records the budget it was handed
  - drive plan -> execute -> execute (two phases)
  - assert phase 2's budget == phase 1's budget minus phase 1's spend
  - assert the total across both never exceeded TaskBudget
```

If this test cannot be written without reaching into `agent_loop`'s
internals, **stop**: the "second harness" warning in
`docs/durable-spec.md:18` is real, and the plan should switch to putting the
task *inside* the agent loop (a much larger change) with that knowledge in
hand. Find this out in days, not weeks.

## 3. Milestone D — size the task, guarantee the lane

### 3.1 D1: a verification floor for every lane

The floor is: **a run that declares checks is not complete until one check's
successful evidence exists after the last mutation.**

Reuse, do not reimplement:

| piece | reuse from | note |
|---|---|---|
| evidence matching | `verification_evidence_passed`, `mod.rs:2173` | already handles the `last_mutation` ordering |
| bounded nudging | `gate_nudge`, `mod.rs:1133` | one budget, capped below the host's continuation cap |
| the gate hook | `contract_gate_continuation`, `mod.rs:1080` | already returns `Some(Value)` to continue the run |

The change is: today the only producer of a contract is plan approval
(`set_active_contract`, called at `mod.rs:2950`). D1 gives it other
producers by making the accessor fall back:

```
active_contract()  ->  explicit plan contract, else
                       declared-check contract, else
                       None
```

**Declared checks need two producers, or D1 is not independent of B.**
There is no existing source of a check command anywhere on this tree: no
`--check` flag in `cli.rs` (42 global flags, none of them a command), and no
`check`/`verify`/`test-command` key among the 67 settings keys. So the
producers are:

| producer | available when | what it is |
|---|---|---|
| `--check <CMD>`, repeatable, persisted per session | **D1 alone** (no B) | a user-declared command, one or more |
| the task's `CheckSpec`s | after B | what D3 plans into the record |

**Deliberately a flag, not a settings key.** A `check` entry in
`settings.json` would be the 68th flat global key — the exact problem §4 of
the companion doc names as the strongest contradiction of "easy to use", and
C3 (the bucket that would fix it) is deferred. A verifier is also
per-project, not per-machine: `cargo test` in this repo, `npm test` in the
next. So `--check` is a per-session flag that persists *with the session*
(next paragraph), and it never becomes a global setting.

D1's first producer is what makes the claim "D1 alone improves every
`normal` run" true — without it, D1's floor is arming from a record that
does not exist yet, and the item ships as dead code behind a
`feature = "durable"` that no default build turns on. That would be the
exact failure mode §2 criticises in durable today.

**Four traps that make this more than a one-line fallback** (found by reading
the gate's own code, and each would ship a broken gate if missed):

1. **`evidence_baseline` must be computed, not left `None`.** The field is
   documented to *fail closed* when `None` (`pir-builtin-mode/src/journal.rs:86-91`):
   "`None` (host could not enumerate the transcript) makes the gate fail
   closed rather than accept unknown history." A synthesised task contract
   that leaves it `None` would nudge every run to the 3-nudge limit and mark
   it UNVERIFIED no matter what the model does. The producer must call
   `shell_call_baseline(&context)` (`mod.rs:2898`) at the same moment plan
   approval does — i.e. **before the phase's first turn**, so pre-existing
   shell calls cannot satisfy the task's checks.
2. **`set_active_contract` resets the pass markers** (`mod.rs:602-609`
   clears `verification_passed_id` and `verified_call`). The declared-check
   fallback must not call it on every read, or a contract that was just
   satisfied is re-armed and the run never settles. Fall back in the
   *getter*, install once.
3. **A satisfied contract is retired, and `--check` must re-arm per task.**
   `complete_contract` (`mod.rs:640-662`) sets `active_contract = None` once
   the evidence passes. That is right for a plan (a plan is executed once),
   but a session hosts many prompts: left alone, the first satisfied check
   silently removes the floor for every later prompt in that session. The
   `--check` producer therefore re-installs a contract — **with a fresh
   `evidence_baseline`** — on each new prompt, not once per session. A stale
   baseline carried over would also let task 1's evidence satisfy task 2's
   check. This is the case a naive implementation gets wrong most quietly,
   because every single-task test passes.

   The hook exists and needs no new plumbing: `before_agent_start` is
   emitted once per prompt (`prompt_loop.rs:110`, inside
   `dispatch_before_agent_start_with_rules` at `:81`) and is already the
   event whose plugin reply the host reads back (`systemPrompt`) — the mode
   plugin has a handler there, so re-arming is a branch in a handler it
   already runs, not a new subscription.

4. **A `--check` contract has no plan, and the prompt hook only injects the
   verification text when the plan is non-empty.** `mod.rs:1583` is
   `Some(contract) if !contract.plan.trim().is_empty() => { ... }`, and the
   `Verification criteria: run one of these commands EXACTLY` block is
   pushed *inside* that arm (`:1596-1608`). With `plan: ""` the whole arm
   is skipped: the model is gated (`contract_gate_continuation` at
   `:1080` does not look at `plan`) but is never told **which** command
   satisfies it. The gate requires verbatim command equality
   (`:2257-2263`, "No substring or shell-semantic parsing"), so a model that
   guesses `cargo test` when `--check` said `cargo test --all` fails three
   nudges and ends UNVERIFIED — the same unknowable-target failure the plan
   lane was built to avoid.

   So D1 must also give the declared-check contract a **plan-equivalent
   body**: the contract's `plan` field carries a synthesised sentence (for
   example "Declared verification for this task; the commands below must
   pass"), or the hook gains a `verification`-only arm that runs when `plan`
   is empty. The second is cleaner — it adds no fake text the model may
   mistake for a task plan — and it is the same handler branch trap 3
   already touches. Neither the plan lane nor its wording changes.

   This is the item that makes "D1 alone is a small change" honest to
   check: without it the floor exists, fires, and is unsatisfiable by
   construction.

So the change is one producer plus one getter branch — still small, but the
"~15 lines" in an earlier revision was optimistic and, worse, would have
been correct-looking and broken at runtime. Revised estimate per producer:
**one function (~25 lines) + a getter branch (~8 lines) + the per-task
re-arm (~15 lines)**, plus the `--check` flag (a normal repeatable clap field
and the per-session record that carries it; the flag is the only new
user-visible surface D1 adds, and §4's reasoning is why it is not a settings
key).

The producer is small because the types already fit: `Verification`
(`pir-builtin-mode/src/journal.rs:43`) is `Vec<String>` of exact commands,
which is what `--check` is, and `approval_id` already falls back to the
literal `"plan"` (`mod.rs:1086-1089`) when absent — so a declared-check
contract needs no approval record to reach the gate.

Accepting:

```
tests/verification_floor_normal.rs
  - normal lane, one check declared via --check
  - mock model claims done without running the check  -> run is NOT complete,
    one nudge, run continues
  - mock model runs the check, then makes another edit, then claims done
    -> still NOT complete (the last_mutation ordering)
  - mock model runs the check last                                -> complete
  - a check that was already run BEFORE the session started does not count
    (the evidence_baseline case)
  - after the run completes, a second settle does not re-arm the gate
    (the set_active_contract reset case)
  - two prompts in ONE session: the second prompt is gated again with its own
    baseline (the complete_contract retirement case)
  - the first captured system prompt of the run CONTAINS the --check command
    text (the plan-empty injection case: without this the gate is
    unsatisfiable by construction)
  - a normal run with NO declared check still settles exactly as today
    (the floor must not change the no-check path)
```

The fourth case catches a naive implementation (free, because
`verification_evidence_passed` already implements it); the fifth and sixth
catch traps 1 and 2; the seventh catches trap 3; the eighth catches trap 4
and is the cheapest of them all — it only reads the captured prompt; the
ninth is the regression guard for the whole item, because D1 must be a no-op
when nothing is declared.

`--check` has to survive the session, not just the run: a task record that
resumes must keep the same checks, so it is persisted with the session's
settings (and, once B lands, copied into the record). One flag, one store,
no second source of truth — which is also why traps 1 and 3 both hinge on
recomputing the baseline from the *session* rather than carrying it.

### 3.2 D2: sizing from inputs the harness already has

The signal must be **a pure function of observable inputs**, so it can be a
regression test. Inputs available before turn one:

| input | stage | source | why it is a signal |
|---|---|---|---|
| files named in the prompt | D2a | existing `@file` parsing | a named file is usually the whole scope |
| touched-module count | D2a | a bounded `find` over the cwd | a repo with 3 modules is not the same task as one with 90 |
| deliverable count / step sequence in the prompt | D2a | punctuation + conjunction heuristics over the prompt text (measurable, no model call) | catches `c3`-shaped tasks: cheap in tokens, multi-phase in shape |
| previous attempt in this task | D2b | B's checkpoint (the attempt ledger) | already failed once → do not start small again |

Deliberately **not** inputs, with the reason: conversation length (a long
chat does not make the next prompt large), model choice (a bigger model is
not a bigger task), and token count alone (see the `c3` case below).

Signature:

```rust
/// v1: no registry, no config. A pure function of the observable inputs
/// above, so a unit test can pin every row of the table.
pub fn size_task(input: &TaskInputs) -> TaskSize;

/// Everything D2a needs is in these three fields; `failed_attempts` is
/// `None` until B1 lands, which is what makes the two stages one type.
pub struct TaskInputs {
    pub named_files: Vec<String>,
    pub touched_modules: usize,
    pub prompt_shape: PromptShape,
    pub failed_attempts: Option<u32>, // D2b
}

pub enum TaskSize { Small, Medium, Large }

impl TaskSize {
    /// Recorded in the task ledger by D3. A wrong guess must be explainable,
    /// so the reason is data, not a log line.
    pub fn reason(&self) -> &'static str;
}
```

`size_task` deliberately does **not** return a `Lane`. Sizing lives in
`pir-builtin-mode` (engine-free, testable without a session); the
size → lane mapping lives in `pir-core`, which is the only crate that sees
both `pir-builtin-mode` and `pir-durable` (see §2.1). Keeping them apart is
what lets sizing be wrong without silently changing a guarantee — D3 owns
the mapping and refuses a contradiction.

**D2 splits, and the split is what makes the order executable.** `size_task`
ships in two stages because one of its inputs reads the task record:

| stage | inputs | ships |
|---|---|---|
| D2a | named files, touched-module count, prompt shape | with D3 (no task record) |
| D2b | + "this task already failed once" (B's ledger) | after B1 |

D3 depends on `size_task`, so D2a cannot come after D3 — an earlier revision
listed D3 before D2 and claimed three lanes at once, which is not
executable. The `TaskInputs` struct carries the ledger-derived field as
`Option`, so D2b is additive and the function's two stages are one type.

The regression fixture already exists — `RESULTS.md:211-214` records
`s1-duration` 12,523 tok / 5 turns, `s2-slugify` 16,435 / 6 (short), and
`l1-ledger` 219,700 / 14, `c3-two-turn` 24,954 / 9 (long). Write the table
test **against those**, so the function is pinned to real tasks rather than
invented ones.

One thing the fixture already shows and sizing must respect: **token count
and turn count do not agree on what "large" is.** `l1-ledger` is the large
task by both measures (219,700 / 14), but `c3-two-turn` is 24,954 tokens in
9 turns — cheap, yet it is a plan→implement session whose *shape* is
multi-phase. A function that ranks purely on tokens calls `c3` small. So D2
must read at least one shape signal (does the prompt name more than one
deliverable / a sequence of steps) alongside the size signals, and the `c3`
row is the case that proves it.

**Non-goal, restated:** never ask the model to rate difficulty. That is
unmeasurable and it is the one thing §1 of the companion doc argues against.

### 3.3 D3: auto lane selection

The mapping lives in `pir-core` (§2.1), because it is the only crate that
sees both sides:

```
Small  -> Mode::Normal   + D1's checks armed   (no plan round-trip)
Medium -> Mode::Normal   + D1's checks armed   (see below: plan needs a human)
Large  -> Mode::Foreman                        (a reviewer must return PASS)
```

A lane is therefore **(mode, whether D1's floor is armed, which tool set is
declared)** — not just a mode. `Mode::Normal` appears twice above with
different guarantees, which is exactly why the lane cannot be a `Mode` and
why the record stores the lane's *name and reason* rather than an enum
(§2.1).

**Small and Medium differ only in where the checks come from, and that is
weaker than it sounds.** Both are `Mode::Normal` with D1's floor; Small's
checks are the `--check` line, Medium's would be the checks of a plan the
model wrote itself. So the two lanes are the *same mechanism* with a
different producer, and the honest statement is:

| lane | guarantee, headless | what actually differs |
|---|---|---|
| Small | D1's floor over `--check` | nothing else |
| Medium | D1's floor over the checks a plan phase wrote | needs B (or the deferred plan-proposal option) before it exists at all |
| Large | foreman's independent reviewer | a different gate entirely |

That means D3's Medium row is a **future** state, not something D3 can ship
before either B lands or plans can be proposed without approval. Shipping
D3 ahead of B gives two lanes in practice (Small, Large), and that is fine —
but the lane table must not claim three when one of them has no producer
yet. D3's acceptance therefore covers Small and Large, and Medium's row is
gated on B1.

**Medium cannot be the plan lane in a headless run, and that changes the
requirement.** `submit_plan` (`mod.rs:1662`) does not approve anything: it
creates an `ApprovalKind::Plan` record in `Requested` state
(`request_plan`, `mod.rs:515-570`) and blocks the tool call with
`plan_approval_block_reason` (`pir-builtin-mode/src/delegation.rs:211-217`),
which tells the model to "STOP now and end your turn". Approval only
happens through `decide_approval` (`mod.rs:458`), driven by TUI `/approvals`
or `pir foreman approve <id>` (`pir-core/src/foreman.rs:129`). In `pir -p
"…"` there is no one to type either, so a Medium task routed to `plan`
would end with a pending approval and no work done — a long wait for a
decision nobody can make.

So the lane table above is the honest one: `Medium` is **`normal` + D1's
checks**, and what makes it stronger than `Small` is not the mode but
(a) it starts from a plan the model wrote and (b) its checks come from that
plan rather than a one-line flag. Two ways to keep a real plan lane, both
deferred to 0.3.5 rather than silently assumed:

| option | why deferred |
|---|---|
| auto-approve a plan when the request is non-interactive | it deletes the human gate that is the point of plan mode; needs its own decision |
| let the model *propose* verification commands and arm them without approval | same gate, same decision, and it needs the "is this command safe" question answered |

D1 makes Medium real without either: `--check` (or the model's own
declared checks once B lands) supplies the verification, and `normal` runs
it. That is why D1 is worth shipping before D3 — D3's Medium lane depends
on it, and nothing else.

- selection happens once, before turn one, and the result is written to the
  task ledger (lane name, reason)
- a mid-run `/mode` that contradicts the chosen lane is **refused** with the
  recorded reason rather than silently changing the guarantee
- a run started with no `/mode` in a non-interactive invocation never
  selects a lane that requires a human decision
- accepting, shippable without B (two lanes): a run started with no `/mode`
  reports its lane and reason; a Small run's check gate fires and a Large
  run's reviewer gate fires; a `pir -p` run whose prompt sizes Medium
  finishes with no pending approval (it runs as Small's mechanism)
- accepting, after B1 (third lane): a Medium run's checks come from the
  planned phase rather than `--check`, and the ledger records that source

The Medium row is gated on B1 on purpose. Claiming three lanes before the
third has a producer is exactly the kind of unmeasured claim §1 of the
companion doc warns about.

### 3.4 D4: escalation only

```
attempt 1 fails check -> rework within the same lane
attempt 2 fails check -> escalate one lane up, record it
never de-escalate automatically
```

Escalation is written to the task ledger as a `JournalEvent`-shaped record
(reuse the shape at `pir-builtin-mode/src/journal.rs:406`), so the history is
auditable and a resumed task knows which lane it is on.

**Two counters that must not be confused.** D1's gate nudges the model up to
its own cap *within one attempt* before that attempt is declared UNVERIFIED
(`gate_nudge`, `mod.rs:1133`). D4 counts **failed verify phases**, not
nudges: one verify that ends UNVERIFIED is one failed attempt. Wiring D4 to
the nudge counter would escalate a task that was merely slow to run its check,
so the attempt ledger is a separate field in the task record, incremented by
the `verify` phase and by nothing else.

**Escalation raises the guarantee, not necessarily the cost.** §1.2 of the
companion doc measured `plan` *more* expensive than `foreman` on one task
(1,147,051 vs 776,419 tokens), so "one lane up" is a stronger check, not a
cheaper or dearer one. That is also the reason escalation stops at the
`Reviewed` lane: there is no fourth guarantee above an independent reviewer,
and adding one would be a new mechanism, not a new rung.

### 3.5 D5: declare only the tools the lane needs

This is the "efficient" half, and the one item that lowers the recurring
per-turn cost without a second binary.

Today the default declares 12 tools = **15,670 B** of `tools[]` on **every**
turn (real capture, plan §1.4). A small task needs four. The mechanism
exists — and better than expected: `declared_active_tools`
(`agent_session/tools.rs:265-280`) resolves the declaration set through
`active_tools_override`, which `PluginHost::active_tools_override` already
exposes. So D5 needs **no new plumbing**: the mode plugin only has to return
the lane's set from the hook it already has. The registry is never filtered
("F12"), so nothing becomes unreachable.

**D5 does not invent tool selection, and must not become a second one.**
`--perf-profile efficient` / `PIR_PERF_PROFILE=efficient` already narrows
the declaration to `DEFAULT_TOOL_NAMES = ["read","bash","edit","write"]`
(`config/settings/tools.rs:24`) through `declared_active_tools`
(`agent_session/tools.rs:276-284`). That set is *exactly* the small lane's
table row below, so **D5's small-lane byte win is already reachable today**
by an opt-in flag. What D5 actually adds is narrower and should be stated as
such:

| D5 adds | already available | honest value |
|---|---|---|
| automatic per-lane selection (no flag to remember) | `--perf-profile efficient` | a default, not a capability |
| the lane → tool set for the *medium* lane (`+tool_search`) | nothing | small |
| lane-beats-profile precedence (below) | nothing; today they conflict | **a real bug fix** |

So D5 is not "unlock a 15,670 B → 4,000 B saving"; that saving exists and a
user who knows the flag already gets it. D5 is "make the right declaration
the default for the lane, and stop `efficient` from breaking foreman".
Measured honestly, D5 is the least valuable of the five D items, and if the
schedule tightens it is the one to drop — dropping it costs no correctness,
only a flag.

That also explains the precedence problem: `efficient` exists and is a
global opt-in that also lowers output caps and compaction reserves
(`build.rs:789-794`), so it is not going away. D5 is the lane dimension of a
control that already has a profile dimension, and the order must be
explicit:

| precedence | source | when |
|---|---|---|
| 1 | explicit `--tools` / `setActiveTools` override | user said exactly what they want |
| 2 | mode plugin's lane set (D5) | the lane chose it |
| 3 | `PerformanceProfile::Efficient` → 4 core tools | profile only |
| 4 | `None` → every registered tool declared | balanced default (today's behaviour) |

The one conflict to fix, not paper over: `Efficient` + small lane both mean
the same four tools, so the two agree today; `Efficient` + `large` would
strip foreman's `subagent`, which foreman cannot work without. Lane (2) must
therefore win over profile (3), or `Efficient` in a foreman session ships a
mode that cannot delegate. That is a two-line precedence change in
`declared_active_tools`, and it is the only edit D5 makes to that function.

| lane | declares | rationale |
|---|---|---|
| small (`normal` + D1) | `read`,`bash`,`edit`,`write` (+`grep`/`find`/`ls` when the sizing signal saw a search-shaped prompt) | the upstream four; a one-file fix needs nothing else |
| medium (`normal` + D1, checks from the plan; needs B1) | the small set + `tool_search` | the task may need a tool the selector did not predict |
| large (`foreman`) | read-only set + `subagent` + `todo` — already the mode's own contract (`MODE_ALLOWED_TOOLS`) | unchanged; foreman restricts itself today |

Accepting:

```
tests/lane_tool_declaration.rs
  - a small-lane run declares <= 6 tools and its captured tools[] is
    under 10,000 B
  - a tool that was NOT declared is still callable through tool_search
    (the registry is not filtered -- the property F12 documents)
  - switching lane mid-task changes the declaration set on the next turn
  - `performance.profile = "efficient"` + large lane still declares
    `subagent` (lane beats profile -- otherwise foreman cannot delegate)
  - explicit `--tools read` still overrides the lane (user beats lane)
```

The third case stops D5 becoming a locked-in guess: the declaration follows
the lane, and D4 can escalate the lane. The fourth and fifth pin the
precedence table above, which is the part most likely to be quietly wrong:
without them, `efficient` is a profile that can break foreman.

> **Honest risk, and D5's real value.** Two separate reservations:
>
> 1. D5 assumes models call `tool_search` instead of asking for a tool they
>    were not handed. `RESULTS.md` supports *removing* tools nobody calls
>    (`ctx_*`: zero calls in six runs) but has no evidence for
>    *hide-then-discover*. The acceptance pins the mechanism; whether models
>    use it well is a post-D3 measurement on real tasks.
> 2. As the table above states, the small-lane payload is already reachable
>    via `--perf-profile efficient`. So D5's value is "the right default" plus
>    one genuine bug fix (lane vs profile precedence), not a new capability.
>    **If the schedule tightens, D5 is the D item to drop** — it costs no
>    correctness, only a flag users would have to know.

## 6. Order, and what each step buys

| step | buys | if it fails |
|---|---|---|
| D1 | **every** `normal` run with a declared check gains a correctness floor (`--check` needs no B) | nothing lost; it is the first item |
| D2a | the three-input sizing function (no ledger) | D3 falls back to a fixed threshold |
| D3 (two lanes) | automatic Small/Large selection with their guarantees | users keep choosing `/mode` manually |
| D5 | the right per-lane declaration is the default, and `efficient` stops breaking foreman | declare the medium set everywhere — a flag users keep using |
| C1/C2 | a first five minutes with a path through it | nothing else is affected |
| B2 test | proof the task record can drive the loop without touching it | stop; re-plan with the proof in hand, everything above already shipped |
| B1 | a persistent task record that reopens from disk | still useful as a library |
| B3 | crash-resumable tasks | falls back to B1 |
| D2b | sizing gains the "already failed once" input | sizing keeps three inputs |
| D4 | failure escalates instead of silently finishing | lane stays where it started |
| D3 (medium) | the third lane, with checks from a planned phase | Small absorbs Medium; the ledger records one fewer source |

D1 is the highest value per line changed in this whole document — a fallback
in one accessor plus a baseline plus one flag, and it is the item that makes
"small tasks execute correctly" a property rather than a hope. It is also
the one item that is genuinely independent of B: `--check` is its own
producer, so D1 can ship in 0.3.4 even if B slips.

The table's first five rows are a **complete release on their own**:
D1 + D2a + D3's two lanes + D5 + C1/C2 needs no task record. That is the
shape to ship if B2's go/no-go fails.

There is **no light profile** in this release: `full` is the only shipped
binary. `pir-minimal` stays as the zero-feature developer probe.
