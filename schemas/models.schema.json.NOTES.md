# `models.schema.json` — upstream alignment status (updated 2026-10-26)

**Status: ALIGNED, with two recorded intentional differences.** The artifact is
generated by `src/config/schema.rs::models_schema()` and now reproduces the
upstream shape (`packages/coding-agent/schemas/models.schema.json`, pi 1.4.0,
commit `38ff99177fba21e9c57a670f4e95adcf407c99c7`) except for the pir-only
runtime fields listed below.

| Artifact | Path | Size |
|---|---|---|
| Committed schema (aligned) | `schemas/models.schema.json` | 47,293 B |
| Generator / source of truth | `src/config/schema.rs::models_schema()` | — |
| Upstream schema | `pi/packages/coding-agent/schemas/models.schema.json` | 46,008 B |

A recursive structural comparison of the committed file against upstream
reports **zero value differences on every shared path** (types, `required`,
`const`, descriptions, bounds). The only path-set differences are the ones
below.

## What is aligned

- **Root**: upstream `$comment` instead of pir's former
  `title`/`description`/`additionalProperties: false`; `required: ["providers"]`
  and `type: object` unchanged. Unknown top-level keys validate (upstream
  default `true`).
- **Provider map and nested maps** use
  `patternProperties: { "^.*$": … }`: `providers`, provider/model `headers`,
  `samplingParams`, every `samplingParamsByThinkingLevel` level, and
  `modelOverrides`. No `additionalProperties` remains on the provider object,
  `models[].`/`modelOverrides[]` objects, or their nested maps, so upstream
  keys pir does not know still validate.
- **`$defs`**: `ModelCost`, `ModelInputLimits`, `ModelPromptCache`,
  `ThinkingLevelMap` restored next to `ProviderCompat`; `models[].cost` and
  `compat.allowedFallbackModels[].cost` now `$ref` `ModelCost`.
- **Cost**: `ModelCost` requires all four rates (`input`, `output`,
  `cacheRead`, `cacheWrite`) and every rate is `type: number` (no `minimum`,
  upstream parity); `cost.tiers[]` requires `inputTokensAbove` plus the four
  rates and uses a numeric `inputTokensAbove`. `modelOverrides[].cost` keeps
  upstream's inline, non-required patch shape (rates merge per field).
- **Model tokens**: `contextWindow` / `maxTokens` are `type: number` with
  `exclusiveMinimum: 0` (defaults 128000 / 16384 on `models[]` only).
- **`apiKey`** is the upstream string template (`type: string`,
  `minLength: 1`) — pir's runtime field is `Option<String>`, so the former
  `anyOf[string, integer]` documented a value the loader rejects.
- **`oauth`** is `{ "type": "string", "const": "radius", … }`.
- **Descriptions** (`compat` `$ref` site, `cacheRead`/`cacheWrite`, cost
  tiers, `apiKey`) match upstream verbatim.

## Residual differences (intentional)

### 1. `ProviderCompat` pir-only fields

pir carries five knobs on the compat block that upstream keeps on `Model` or
only has at provider level. They stay in `$defs.ProviderCompat` because the
runtime (`src/ai/types/model/compat.rs::OpenAiCompat`) needs them:

| Field | Why pir keeps it |
|---|---|
| `samplingParamsByThinkingLevel` | routed there by `PiModelConfig` |
| `customHeaders` | extra static headers in `OpenAiCompat` |
| `inputLimits` | model input limits carried on compat |
| `promptCache` | prompt-cache metadata carried on compat |
| `authHeader` | provider-level flag mirrored onto the model |

`inputLimits` / `promptCache` are `$ref`s to the shared `$defs`. The schema
therefore has 45 compat properties: the 40 upstream ones pir consumes plus
these five.

### 2. Upstream-only `ProviderCompat` fields are NOT documented

Upstream 1.4.0 also has `imageInput` and `sendImageOptInHeader`. pir's
`OpenAiCompat` has no corresponding field and no adapter reads them, so the
published schema deliberately omits them instead of advertising unsupported
configuration. `compat.additionalProperties` stays `true` (upstream parity),
so a `models.json` using them still validates — it is just not autocompleted.
Add them here only with the runtime field that consumes them.

### 3. `modelOverrides` entry extras

pir's override schema keeps `id`, `baseUrl` and `api` on top of upstream's
partial model shape, and the block keeps its description ("Per-model overrides
applied last, to chat models only."). `apply_pi_model_override` honors
`baseUrl`/`api`; `id` is part of `PiModelConfig` but the map key selects the
model. Unknown keys validate on both sides, so this is additive documentation,
not a stricter gate.

## Runtime notes (not schema differences)

- `PiCostRates` reads only the four flat rates; `cost.tiers` is accepted and
  ignored by the `models.json` loader (the upstream-shaped schema still
  documents tiers for editor/validator consumers). Tiered pricing comes from
  the generated catalog, not from `models.json`.
- `contextWindow` / `maxTokens` are `u64` in `PiModelConfig`, so the loader is
  stricter than the published `number` schema (fractional values fail to
  deserialize). The schema follows upstream.
- Header values are documented as strings (upstream parity); pir's loader also
  accepts JSON `null` as a "suppress this default header" marker.
